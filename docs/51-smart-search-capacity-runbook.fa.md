# ۵۱. چک‌لیست اجرای ظرفیت و صف سرچ هوشمند

این سند ترتیب دقیق کارهایی است که روی سرور باید انجام شود تا صف و ظرفیت جدید فعال شود. هر مرحله «دستور»، «نتیجهٔ درست» و «اگر نشد» دارد. تصمیم‌ها و عددها در [۵۰](50-smart-search-capacity-queue.fa.md) است؛ این‌جا فقط اجرا.

مایگریشن تازه‌ای لازم نیست؛ تغییرها فقط کد و تنظیمات‌اند.

---

## مرحله ۰ — قبل از هر کاری

1. وضعیت فعلی را ثبت کن تا بعداً مقایسه داشته باشی:
   ```
   curl -s -H "Authorization: Bearer $ADMIN_TOKEN" \
     "https://api.pharmenta.ir/api/v1/ai-lab/status/?diagnostics=1" | python -m json.tool
   ```
   مقدار `runtime.capacity` باید ۲ باشد و `job_cache_backend` باید Redis باشد (نه LocMem).
2. از دیتابیس بکاپ بگیر.
3. مطمئن شو `THROTTLE_CACHE_URL` روی **همهٔ** سرویس‌ها (وب و ورکر) یکی است؛ اسلات‌ها آن‌جا نگه داشته می‌شوند.

## مرحله ۱ — متغیرهای محیطی

روی **سرویس وب** و **ورکر Celery**، هر دو، این‌ها را ست کن (مقادیر باید یکسان باشند):

```
AI_LAB_MAX_CONCURRENT_JOBS=8
AI_LAB_MAX_CONCURRENT_SLOTS=64
AI_LAB_QUEUE_MAX_LENGTH=200
AI_LAB_QUEUE_ETA_SECONDS=20
AI_LAB_QUEUE_PROMOTE_SECONDS=5
AI_LAB_QUEUE_MAX_WAIT_SECONDS=600
```

نتیجهٔ درست: `runtime.capacity` در همان اندپوینت مرحلهٔ ۰ حالا ۸ نشان می‌دهد.

اگر نشد: اگر رفتار قدیمی (۴۲۹ فوری) ماند، یعنی نسخهٔ جدید کد مستقر نشده است؛ مرحلهٔ ۳ را اول انجام بده.

## مرحله ۲ — هم‌زمانی ورکر

دستور بالا آمدن ورکر را طوری تنظیم کن که هم‌زمانی کمی بیشتر از اسلات‌ها باشد:

```
celery -A config worker -Q ai_search -c 10 -l warning
```

نتیجهٔ درست: `celery -A config inspect stats` مقدار concurrency را ۱۰ نشان می‌دهد.

## مرحله ۳ — استقرار کد

شاخه را مستقر کن (بدون مایگریشن). بعد چک کن:

```
python manage.py check
python manage.py promote_ai_search_queue
```

نتیجهٔ درست: خروجی `waiting=0 promoted=0`.

## مرحله ۴ — تور ایمنی صف

اگر beat داری: هیچ کاری لازم نیست (`ai-lab-promote-queue` هر ۵ ثانیه خودکار اجرا می‌شود).

اگر beat نداری، یکی را انتخاب کن:

- cron هر دقیقه (برای محیط بدون beat کافی است):
  ```
  * * * * * python manage.py promote_ai_search_queue
  ```
- یا سرویس همیشه‌روشن:
  ```
  python manage.py promote_ai_search_queue --loop --interval 5
  ```

## مرحله ۵ — تست دود (بدون فشار)

با یک حساب آزمایشی دو جست‌وجوی پشت‌سرهم بفرست؛ دومی باید `429 AI_LAB_BUSY` بگیرد (نه به‌خاطر ظرفیت، به‌خاطر قفل «یک جست‌وجوی فعال برای هر کاربر»). این یعنی قفل هر کاربری سالم است.

## مرحله ۶ — تست بار واقعی

```
python tools/smart_search_load_test.py \
  --base-url https://api.pharmenta.ir/api/v1 \
  --tokens-file tokens.json --count 8 --json-out load-8.json
```

فایل `tokens.json` یک لیست JSON از توکن‌های حساب‌های آزمایشی است (هر توکن = یک کاربر شبیه‌سازی‌شده). با ۸، ۱۶ و ۳۲ اجرا کن و بین اجراها ۵ دقیقه صبر کن تا صف خالی شود.

معیار پذیرش:

| شاخص | حد قابل قبول |
|---|---|
| `submit_codes` | همه ۲۰۲ (هیچ ۵۰۰، هیچ ۴۲۹) |
| `complete_p95` | زیر ۴۵ ثانیه با ۸ اسلات |
| خطاهای ورکر | هیچ `PROVIDER_*` و هیچ ۴۲۹ از سمت GapGPT |
| `queue_wait_ms` در لاگ | زیر ۶۰ ثانیه در بار ۱۶ کاربر |

اگر ۴۲۹ از سمت GapGPT دیدی، اسلات را پایین نیاور؛ سهمیهٔ پلن را بالا ببر یا صف را طولانی‌تر بپذیر.

## مرحله ۷ — پایش ۲۴ ساعت اول

در لاگ ورکر، هر چند ساعت:

```
grep reference_search_metrics <log> | tail -50
grep AI_LAB_QUEUE_FULL <log>
grep '"outcome":"failed"' <log>
```

نتیجهٔ درست: `AI_LAB_QUEUE_FULL` صفر، `outcome:failed` نزدیک صفر، و `queue_wait_ms` در ساعات اوج زیر یک دقیقه.

## مرحله ۸ — تصمیم بعدی

| اگر دیدی | کار |
|---|---|
| صف در اوج مدام بالای ۲۰ نفر | اسلات را ۱۲ یا ۱۶ کن و ورکر را متناسب بزرگ کن |
| `queue_wait_ms` بالا ولی CPU ورکر پایین | گلوگاه ارائه‌دهنده است؛ سهمیهٔ GapGPT را بالا ببر |
| خطای حافظه یا swap در ورکر | اسلات هر ورکر را کم کن و ورکر دوم اضافه کن |
| هزینهٔ توکن غیرمنتظره | سهمیهٔ ساعتی هر کاربر و قیمت اعتبار را بازبینی کن |

## مرحله ۹ — بازگشت (Rollback)

برای برگشتن به رفتار قبلی (رد فوری به‌جای صف) کافی است:

```
AI_LAB_QUEUE_MAX_LENGTH=0
```

و ری‌استارت وب و ورکر. بعد از آن هر درخواست اضافه `429 AI_LAB_QUEUE_FULL` می‌گیرد.

## مرحله ۱۰ — کار باقی‌ماندهٔ فرانت

API الان `queue_position` و `eta_seconds` را می‌دهد؛ صفحهٔ سرچ هنوز نشانش نمی‌دهد. تا آن موقع کاربر با اسپینر منتظر می‌ماند ولی نمی‌داند چند نفر جلوتر است.
