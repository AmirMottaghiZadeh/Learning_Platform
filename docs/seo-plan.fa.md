# برنامهٔ سئوی فارمنتا برای داروسازان و مراجع علمی حرفه‌ای

تاریخ بررسی: ۲۱ اکتبر ۲۰۲۶، منطقهٔ زمانی تهران.
مخاطب اصلی طبق انتخاب مالک: داروسازان و کاربران حرفه‌ای منابع علمی؛ زبان اولیه: فارسی.
هدف پیشنهادی: تبدیل جست‌وجوی مرتبط به استفاده از وب‌اپ، ثبت‌نام و خرید اشتراک.

این سند برنامهٔ اجرایی و راهنمای تنظیمات است. بررسی کد و خواندن صفحات عمومی انجام شده؛
اصلاحات فنی، ساخت حساب گوگل، تغییر DNS، ذخیرهٔ تنظیمات روی سایت و انتشار محتوا هنوز انجام نشده‌اند.
به دادهٔ خصوصی Search Console، Analytics، حجم جست‌وجو یا حساب پنل دسترسی نداشته‌ایم.
کلمات کلیدی این سند پیشنهاد اولیه‌اند و به‌معنای اثبات پربازدیدبودن یا کم‌رقابت‌بودن نیستند.

## ۱. نتیجهٔ بررسی واقعی سایت

صفحهٔ اصلی، بلاگ، robots.txt و sitemap نسخهٔ عمومی خوانده شدند.

| مورد | یافتهٔ مشاهده‌شده | نتیجه برای برنامه |
|---|---|---|
| صفحهٔ اصلی | پاسخ HEAD برابر HTTP 200؛ عنوان «فارمنتا \| اپ آموزشی دارویی» | عنوان و معرفی باید با مخاطب حرفه‌ای دقیق‌تر هماهنگ شود |
| canonical خانه | `https://pharmenta.ir/` | پایهٔ درست موجود است |
| توضیح خانه | «درسنامه دارویی ، فلش کارت ، آزمون به زبان فارسی و انگلیسی / رفرنس های مرجع بالینی» | متن یکپارچه و مبتنی بر امکانات واقعاً فعال تهیه شود |
| ایندکس خانه | متای noindex در HTML بررسی‌شده دیده نشد | بررسی نهایی با URL Inspection لازم است؛ نبود noindex اثبات ایندکس‌شدن نیست |
| بلاگ | پیام «هنوز مطلبی منتشر نشده است.» | مانع اصلی رشد محتوایی فعلی، نبود مقالهٔ عمومی است |
| sitemap | ۹ نشانی؛ خانه، بلاگ، پلن، دانلود، اطلاعیه‌ها، حریم خصوصی، درباره، قوانین، تماس | در زمان بررسی مقاله‌ای در نقشه نبود؛ تعداد، هدف سئو نیست |
| robots | اجازهٔ خزیدن عمومی و مسدودکردن پنل، عملیات، حساب، خرید، پرداخت و لینک دانلود | برای شروع نیاز به افزودن خطوط ندارد |
| تأیید و تحلیل‌گر | متای google-site-verification و اسکریپت شناخته‌شدهٔ تحلیل‌گر در خانه و بلاگ دیده نشد | مالک نیز اعلام کرد حساب‌ها هنوز راه‌اندازی نشده‌اند |
| اشتراک‌گذاری خانه | Open Graph موجود؛ og:image در خروجی بررسی‌شده نبود | تصویر پیش‌فرض اختصاصی اضافه شود |
| دادهٔ ساختاریافته | Organization در خانه موجود است | تکمیل هویت واقعی برند و اعتبارسنجی لازم است |

این بررسی، خزیدن کامل سایت یا ارزیابی Core Web Vitals نیست. هیچ نمرهٔ سرعت، رتبه،
تعداد صفحات ایندکس‌شده یا میزان بازدید تخمین زده نشده است. بررسی HTTP، www، همهٔ صفحات
داخلی، گواهی SSL همهٔ زیردامنه‌ها و رفتار خزنده‌ها در لاگ سرور به مرحلهٔ فنی موکول است.

## ۲. مبنای به‌روز برنامه

- در تاریخ بررسی، تازه‌ترین رخداد رتبه‌بندیِ فهرست رسمی گوگل «September 2026 spam update»
  با شروع ۲۴ سپتامبر ۲۰۲۶ بود. این یک واقعیت تاریخی است، نه نسخه‌ای از الگوریتم برای نصب روی سایت. [G1]
- مستند تولید محتوای هوش مصنوعی در ۱ اکتبر ۲۰۲۶ به‌روزرسانی شده است. تولید انبوه صفحات
  بدون ارزش افزوده، اصالت و نظارت تخصصی مبنای مناسبی برای این سایت نیست. [G2، G3، G4]
- راهنمای جست‌وجوی مولد گوگل بر اصول سئو و محتوای متمایز تأکید می‌کند؛ فایل llms.txt یا
  ترفند ویژهٔ AEO/GEO شرط حضور در جست‌وجوی گوگل نیست. [G5]
- FAQ rich result از ۷ مهٔ ۲۰۲۶ در نتایج گوگل نمایش داده نمی‌شود؛ بنابراین وقت توسعه را
  صرف وعدهٔ نمایش FAQ در نتایج نمی‌کنیم. بخش پرسش‌وپاسخ مفید روی صفحه همچنان قابل استفاده است. [G2]
- در موضوعات اثرگذار بر سلامت، دقت، اعتماد، تخصص واقعی و شفافیت نویسندگی اولویت دارند.
  E-E-A-T یک امتیاز عددی در پنل یا افزونه‌ای برای خرید نیست. [G4]

## ۳. تنظیمات دقیق پنل، قابل اجرا توسط مالک

نشانی تنظیمات: `https://pharmenta.ir/panel/settings/?tab=seo`

| فیلد | مقدار یا اقدام پیشنهادی | روش کنترل |
|---|---|---|
| پسوند عنوان | `\| فارمنتا` | عنوان مقاله پسوند برند را فقط یک بار داشته باشد |
| کد تأیید گوگل | پس از ساخت URL-prefix property، فقط مقدار `content` تگ HTML | View Source صفحهٔ اصلی؛ سپس Verify در Search Console |
| خطوط اضافه robots.txt | فعلاً خالی بماند | فایل فعلی مسیرهای خصوصی و Sitemap را خودکار تولید می‌کند |
| جلوگیری از ایندکس کل سایت | در سایت اصلی خاموش، پس از کنترل آماده‌بودن محتوای عمومی | HTML و HTTP header و URL Inspection بررسی شوند |
| کد تحلیل‌گر head | فقط کد وابسته به شناسهٔ واقعی GA4؛ نمونه در `seo-ga4-head.html` | یک page_view در DebugView و Realtime، بدون ثبت دوباره |

وجود فیلد خالی به‌معنای نیاز به پرکردن آن نیست. robots.txt فعلی این خروجی را خودکار می‌سازد؛
این متن را دوباره در «خطوط اضافه» نچسبانید:

```text
User-agent: *
Allow: /
Disallow: /panel/
Disallow: /ops/
Disallow: /account/
Disallow: /checkout/
Disallow: /pay/
Disallow: /dl/

Sitemap: https://pharmenta.ir/sitemap.xml
```

در این فیلد `Disallow: /`، `Disallow: /blog/`، مسدودسازی `/static/` یا `/media/`،
خط `Noindex:` یا فهرست کلمات کلیدی اضافه نشود. robots.txt کنترل خزیدن است و
به‌تنهایی تضمین حذف نشانی از نتایج یا کنترل دسترسی خصوصی نیست. صفحه‌ای که باید
noindex آن دیده شود باید برای خزنده قابل خواندن باشد. [G6، G7]

### ساخت Search Console از ابتدا

۱. با حساب گوگل متعلق به مالک کسب‌وکار وارد Search Console شوید.
۲. پیشنهاد اصلی: Add property → Domain → مقدار `pharmenta.ir` بدون https یا مسیر.
۳. رکورد TXT دقیق صادرشده توسط گوگل را در DNS فعال دامنه وارد کنید؛ نام معمولاً `@`
یا خالی است، مطابق پنل DNS. مقدار چیزی مانند `google-site-verification=...` است.
۴. پس از انتشار DNS، Verify را بزنید. رکورد را پس از تأیید حذف نکنید.
Domain property پروتکل‌ها و زیردامنه‌ها را پوشش می‌دهد. [G8]

برای استفادهٔ مستقیم از فیلد فعلی پنل، یک URL-prefix property با مقدار
`https://pharmenta.ir/` بسازید و روش HTML tag را انتخاب کنید. نمونهٔ زیر ساختگی است:

```html
<meta name="google-site-verification" content="TOKEN_ISSUED_BY_GOOGLE">
```

فقط `TOKEN_ISSUED_BY_GOOGLE` واقعی را در فیلد پنل بگذارید؛ نه کل تگ و نه
عبارت `google-site-verification=` مربوط به TXT. پنل خودش تگ متا را تولید می‌کند.
برای اثبات این روش، View Source خانه باید همان content را نشان بدهد؛ سپس Verify.
تأیید HTML برای URL-prefix جایگزین تأیید DNS برای Domain property نیست. [G8]

۵. در Sitemaps نشانی `https://pharmenta.ir/sitemap.xml` را ثبت کنید.
۶. خانه و سپس هر صفحهٔ مهم منتشرشده را در URL Inspection با Test live URL کنترل کنید:
HTTP 200، امکان خزیدن، مجوز ایندکس و canonical انتخابی.
۷. Performance و Page indexing را هفتگی بررسی کنید. ارسال نقشه یا درخواست ایندکس،
تضمین ایندکس یا رتبه نیست. فعلاً نبود داده در یک property تازه طبیعی است. [G9، G10]

### ساخت Analytics از ابتدا

۱. در Analytics یک Account متعلق به کسب‌وکار و یک GA4 Property بسازید.
۲. منطقهٔ زمانی گزارش را مطابق عملیات کسب‌وکار، ترجیحاً تهران، انتخاب کنید.
۳. Web data stream با نشانی `https://pharmenta.ir` بسازید.
۴. Measurement ID با قالب `G-...` را از جزئیات stream بردارید.
۵. در فایل `seo-ga4-head.html` مقدار `REPLACE_WITH_REAL_GA4_ID` را عوض کنید،
و کد را در «کد تحلیل‌گر» ذخیره کنید. فقط مدیر اصلی امکان تغییر این فیلد را دارد.
۶. نمونه عمداً تا زمان واردشدن شناسهٔ واقعی، چیزی بارگذاری نمی‌کند.
۷. هم‌زمان همان tag را از GTM یا روش دیگری نصب نکنید؛ هر بار بازشدن صفحه باید یک
page_view داشته باشد. راه‌اندازی GA4 و نصب tag در منابع رسمی توضیح داده شده‌اند. [G11، G12]

برای این سایت، در شروع Enhanced Measurement را خاموش کنید و فقط page_view نمونه را
بسنجید؛ سپس رویدادهای لازم را جداگانه و پس از کنترل payload فعال کنید. نمونه، صفحات
حساب، پرداخت، پنل، نتایج جست‌وجوی داخلی و نشانی‌های دارای پارامتر را کنار می‌گذارد؛
query و fragment را از page_location حذف می‌کند و از referrer فقط مبدأ دامنه را می‌فرستد
تا مسیر قبلی حساب یا توکن پرداخت هم ارسال نشود. در نتیجه ورودهای دارای UTM
و جزئیات کمپین در این نمونهٔ اولیه اندازه‌گیری نمی‌شوند. افزودن attribution نیاز به طراحی جدا دارد.

نام، ایمیل، موبایل، اطلاعات بیمار، مقادیر واردشده در ماشین‌حساب، متن جست‌وجوی دارویی،
توکن پرداخت و کد تأیید را در URL، عنوان یا event به تحلیل‌گر نفرستید. عنوان و نشانی صفحه
ممکن است خودکار جمع‌آوری شوند؛ صرف نصب tag این مسئله را حل نمی‌کند. [G13]
اعلام استفاده از تحلیل‌گر در حریم خصوصی و سازوکار رضایت متناسب با مخاطبان واقعی سایت،
پیش از فعال‌سازی انجام شود. نمونه، مدیر رضایت نیست و شناسهٔ کاربر به گوگل نمی‌فرستد.

این کد فقط سایت Django را اندازه می‌گیرد. نصب آن در پنل، مسیریابی SPA در
`app.pharmenta.ir` یا ثبت‌نام داخل اپ را خودکار پوشش نمی‌دهد؛ وب‌اپ به نصب و رویدادهای
جداگانه نیاز دارد. موفقیت پرداخت نیز باید از تأیید سمت سرور بیاید.

فعال کنترل شود؛ «به‌روز»، «جامع»، «تأییدشده»، وابستگی رسمی به یک ناشر یا تضمین تصمیم
بالینی فقط با شواهد قابل بررسی نوشته شود.

برای دانلود: «دانلود فارمنتا برای داروسازان» و برای پلن‌ها «اشتراک فارمنتا و امکانات هر پلن».
عنوان سئوی هر مقاله موضوع دقیق همان صفحه باشد؛ انباشتن مترادف‌ها در عنوان لازم نیست.
حدود ۵۰–۶۵ نویسهٔ عنوان یا ۱۳۰–۱۶۰ نویسهٔ توضیح فقط راهنمای ویرایشی است؛ گوگل
محدودیت ثابت نویسه برای عنوان تعیین نکرده و ممکن است عنوان نمایش را بازنویسی کند. [G14]

تصویر اشتراک‌گذاری اختصاصی خوانا، مثلاً ۱۲۰۰×۶۳۰، برای برند تهیه شود؛ متن کم و
متناسب با صفحه باشد. این ابعاد پیشنهاد طراحی است، نه عامل تضمین‌کنندهٔ رتبه.

## ۵. معماری صفحات و نقشهٔ کلمات کلیدی

فهرست قابل ویرایش در [seo-keywords.fa.csv](seo-keywords.fa.csv) است. اولویت‌ها
قضاوت اولیه بر اساس تناسب با محصول و قصد کاربرند؛ حجم جست‌وجو و سختی همهٔ موارد
«اندازه‌گیری نشده» است. مسیرهای جدید در CSV پیشنهادی‌اند و هنوز صفحهٔ واقعی ندارند.

| خوشه | عبارت اصلی پیشنهادی | مقصد و نیت |
|---|---|---|
| برند و معرفی | فارمنتا؛ pharmenta | خانه، دانلود و پلن‌ها؛ یافتن محصول |
| مرجع حرفه‌ای | منابع اطلاعات دارویی برای داروسازان | راهنمای جامع انتخاب منابع؛ جذب مخاطب حرفه‌ای |
| بانک اطلاعات | بانک اطلاعات دارویی تخصصی | صفحهٔ معرفی قابلیت واقعی جست‌وجوی دارو و محدودیت‌های داده |
| گایدلاین | راهنمای استفاده از گایدلاین‌های بالینی | مقالهٔ روش کار با منابع و تشخیص نسخهٔ معتبر |
| ماشین‌حساب | ماشین حساب پزشکی برای داروسازان | معرفی ابزارهای واقعاً موجود، ورودی، واحد و منبع |
| طبقه‌بندی | طبقه بندی ATC داروها | راهنمای حرفه‌ای ساختار و استفاده از ATC |
| جست‌وجوی منابع | جستجوی منابع دارویی معتبر | راهنمای قابل اجرا برای پیدا کردن پاسخ مستند |
| تداخلات | منابع بررسی تداخلات دارویی | راهنمای ارزیابی منابع؛ معرفی ابزار فقط در صورت وجود |
| مهارت حرفه‌ای | ارزیابی اعتبار اطلاعات دارویی | راهنمای ارزیابی منبع، تاریخ، پوشش و محدودیت |

هر نیت یک صفحهٔ اصلی داشته باشد؛ «رفرنس دارویی»، «مرجع دارویی» و «منابع اطلاعات
دارویی» برای یک قصد مشابه، سه مقالهٔ تکراری نشوند. برای شکل‌های «گایدلاین/راهنمای
بالینی»، «فارمنتا/pharmenta» و فاصله/نیم‌فاصله از متن طبیعی و دادهٔ جست‌وجو کمک بگیرید.
عبارت‌های بسیار عمومی مانند «دارو» یا جست‌وجوی بیمارمحور، اولویت شروع این پروژه نیستند.

داخل اپ بودن یک قابلیت، وجود صفحهٔ عمومی مناسب جست‌وجو برای آن را تضمین نمی‌کند.
صفحهٔ معرفی عمومی باید بدون ورود HTML مفید، توضیح منبع، نمونهٔ واقعی و مسیر شروع داشته باشد.
اگر ابزار هنوز فعال نیست، صفحه نباید وعدهٔ استفادهٔ فوری بدهد.

### روش تبدیل پیشنهادها به کلمات کلیدی معتبر

۱. برای هر خوشه، نتیجه‌های فعلی جست‌وجو، نوع صفحات، مخاطب و قصد غالب را ثبت کنید؛
رتبهٔ یک جست‌وجوی شخصی یا موتور دیگر، رتبهٔ ثابت گوگل در ایران محسوب نمی‌شود.
۲. اگر دادهٔ حجم از ابزار معتبر با پوشش بازار هدف موجود بود، منبع، کشور، تاریخ و بازهٔ
اندازه‌گیری را کنار عدد ثبت کنید. نبود داده را صفر ننویسید.
۳. پس از جمع‌شدن داده، گزارش Performance را به صفحه، query، دستگاه و کشور تفکیک کنید؛
عبارت‌های برند و غیربرند را جدا ببینید. Search Console همهٔ queryها را نمایش نمی‌دهد. [G9]
۴. بعد از حدود ۴ هفته دادهٔ قابل استفاده، صفحات دارای impression مرتبط و جایگاه حدود
۵ تا ۲۰ را برای بهبود محتوا، عنوان و لینک داخلی بررسی کنید؛ این بازه قاعدهٔ برنامه است.
۵. CTR را در جایگاه و نوع query مشابه مقایسه کنید؛ افزایش impression به‌تنهایی موفقیت
تجاری نیست. هدف، ورود حرفه‌ای مرتبط و استفادهٔ واقعی از محصول است.

انتشار پیشنهادی: هفته‌ای یک تا دو محتوای کامل، متناسب با ظرفیت بازبینی تخصصی؛
تعداد یا طول ثابت، معیار رتبه‌بندی اعلام‌شده از سوی گوگل نیست. [G4]

## ۶. استاندارد محتوای علمی و اعتماد

پیش از انتشار هر محتوای تخصصی:

- نام واقعی نویسنده و بازبین، تخصص قابل احراز و صفحهٔ معرفی آنها مشخص باشد.
- موضوع، مخاطب، محدودهٔ کاربرد، منبع اصلی، نسخه و تاریخ بررسی علمی روشن باشد.
- ارجاع‌ها به ناشر یا سند اصلی وصل شوند و ادعاهای علمی واقعاً با منبع تطبیق داده شوند.
- ارزش افزودهٔ خود فارمنتا مانند جدول، راهنمای روش کار، تصویر و تحلیل روشن باشد.
- تغییر تاریخ فقط پس از تغییر واقعی محتوا انجام شود؛ تاریخ بازبینی از انتشار تفکیک شود.
- بخش «روش تهیه و بازبینی محتوا» و مسیر گزارش خطا در سایت در دسترس باشد.
- استفاده از هوش مصنوعی برای کمک به نگارش با بازبینی انسانی همراه شود و در جای لازم
  روش تولید توضیح داده شود؛ هویت یا صلاحیت ساختگی درج نشود. [G3، G4]

متن عمومی آموزشی یا معرفی منبع، جای توصیهٔ فردی برای بیمار نوشته نشود. جدول یا
خلاصهٔ دارویی تازه، پیش از انتشار به بازبینی متخصص نیاز دارد. دسترسی به متن منابع
حرفه‌ای باید مطابق مجوز واقعی محصول معرفی شود؛ وابستگی رسمی به ناشران ادعا نشود مگر مستند باشد.
در این برنامه تولید یا انتشار خودکار توصیهٔ درمانی انجام نشده است.

## ۷. کارهای فنی با معیار پذیرش

همهٔ ردیف‌های زیر برنامه‌ریزی‌شده‌اند و هنوز در کد اعمال نشده‌اند.

| اولویت | شاهد در مخزن | اقدام | معیار پذیرش |
|---|---|---|---|
| P0 | حساب‌های گوگل ساخته نشده‌اند | راه‌اندازی Search Console و اندازه‌گیری پایه | Verify موفق، sitemap خوانده شود، یک page_view قابل مشاهده |
| P0 | بلاگ عمومی خالی است | انتشار دو راهنمای اولیه با بازبینی حرفه‌ای | محتوای کامل، منبع، نویسنده و CTA واقعی |
| P1 | `views_public.sitemap` از `Post.objects.live()` استفاده می‌کند؛ `live()` شرط noindex ندارد | حذف postهای noindex و نشانی‌هایی با canonical متفاوت از sitemap | تست با مطلب live+noindex و canonical خارجی؛ هیچ‌کدام در نقشه نباشند |
| P1 | `blog_index` صفحه‌های بعد را noindex و canonical را `/blog/` می‌کند؛ category/tag هم query صفحه را از canonical حذف می‌کنند | canonical مستقل صفحهٔ دوم به بعد، هماهنگی سیاست index در همهٔ آرشیوها | با دادهٔ حداقل دو صفحه، `?page=2` canonical خودش باشد؛ لینک پیمایش HTML کار کند [G15] |
| P1 | کارت‌های بلاگ به دسته‌های خالی پیوند دارند | سیاست دسته و برچسب کم‌محتوا | دستهٔ قابل ایندکس، توضیح اختصاصی و محتوای مرتبط داشته باشد؛ صفحهٔ خالی هدف جذب نباشد |
| P1 | title و description خانه از SiteSettings می‌آیند | ثبت معرفی حرفه‌ای و تصویر پیش‌فرض | HTML و Open Graph با محتوای قابل مشاهده سازگار باشند |
| P1 | URLها با `SITE_PUBLIC_URL` ساخته می‌شوند | کنترل canonical همهٔ صفحات و redirect دامنه | یک نسخهٔ HTTPS اصلی؛ HTTP و www بدون زنجیرهٔ غیرضروری به همان مسیر بروند |
| P1 | Article فعلی author URL و معرفی تخصص را ندارد؛ برند ممکن است به‌عنوان Person درج شود | پروفایل واقعی نویسنده/بازبین، serialization امن JSON و نویسنده با نوع درست | JSON قابل parse، بدون خطای Rich Results Test؛ اطلاعات ساختاریافته مطابق صفحه باشد [G16] |
| P2 | Organization ساده در خانه و breadcrumb صرفاً دیداری | تکمیل لوگو، هویت واقعی، sameAs واقعی و BreadcrumbList | اعتبارسنجی بدون خطا؛ مسیر ساختاریافته همان مسیر قابل مشاهده [G17، G18] |
| P2 | favicon فعلی data URL و تصویر OG خانه ناموجود | favicon قابل خزیدن و OG اختصاصی | فایل واقعی قابل دریافت و URL درست در HTML؛ بررسی راهنمای favicon پیش از پیاده‌سازی |
| P2 | فونت‌ها TTF هستند؛ برخی تصاویر فاقد ابعاد HTML هستند | اندازه‌گیری ابتدا، سپس WOFF2، ابعاد/نسبت تصویر و بهینه‌سازی تصویر | مقایسهٔ قبل/بعد؛ نبود جابه‌جایی قابل مشاهده و حفظ کیفیت فارسی |
| P2 | امتیاز داخلی SEO فقط چند شرط طول/تصویر را بررسی می‌کند | تبدیل پیام «بدون مشکل» به توضیح دقیق محدودهٔ چک‌ها | مقالهٔ فاقد مشکلات سطحی به‌عنوان سئوی تضمین‌شده معرفی نشود |
| P2 | برخی امکانات در تنظیمات سرور با feature flag کنترل می‌شوند | تطبیق ادعاهای بازاریابی با استقرار واقعی | هیچ CTA به امکان غیرفعال یا محتوای خالی وعدهٔ دسترسی ندهد |

حذف noindex از آرشیو برچسب، تصمیم عمومی و بدون بررسی نیست؛ دستهٔ مفید و برچسب
کم‌ارزش می‌توانند سیاست متفاوت داشته باشند. جست‌وجوی داخلی دارای `q` همچنان noindex بماند.
صفحه‌های حساب و پرداخت و پنل باید کنترل دسترسی مناسب داشته باشند؛ robots.txt کافی نیست. [G6، G7]

نقشهٔ سایت باید URLهای canonical قابل ایندکس و پاسخ 200 را معرفی کند؛ `lastmod` باید
تغییر واقعی را نشان بدهد. گوگل `priority` و `changefreq` را برای رتبه‌بندی صفحه مصرف
نمی‌کند؛ افزایش عدد priority کار بهینه‌سازی نیست. [G10]

### سرعت و تجربهٔ موبایل

خانه، بلاگ، مقاله، دانلود و پلن‌ها در موبایل با PageSpeed Insights/Lighthouse بررسی شوند؛
برای هر تست تاریخ، URL، دستگاه و شرایط ثبت شود. هدف دادهٔ میدانی صدک ۷۵:
LCP حداکثر ۲٫۵ ثانیه، INP حداکثر ۲۰۰ میلی‌ثانیه و CLS حداکثر ۰٫۱. [G19]
اگر سایت دادهٔ میدانی کافی ندارد، نبود گزارش به‌معنای قبولی یا رد نیست؛ تست آزمایشگاهی
فقط نقطهٔ شروع است. ابتدا منبع واقعی مشکل مشخص شود؛ تصویر LCP را بی‌دلیل lazy نکنید،
تصاویر پایین صفحه lazy باشند، نسبت تصویر رزرو شود و اسکریپت‌های غیرضروری اضافه نشوند.

## ۸. لینک‌سازی و اعتبار بیرونی

هر مقاله از صفحهٔ خوشه و دست‌کم یک محتوای مرتبط پیوند بگیرد، و به مرجع اصلی و
یک مقصد محصول مرتبط وصل شود. این تعداد، قاعدهٔ ویرایشی برنامه است، نه فرمول گوگل.
انکرتکست دقیق و طبیعی باشد؛ صفحهٔ بدون لینک ورودی داخلی منتشر نشود.

برای اعتبار بیرونی، راهنمای اصیل یا ابزار مفیدی بسازید که انجمن، دانشگاه یا رسانهٔ
تخصصی واقعاً بخواهد به آن ارجاع دهد. معرفی مهمان با هویت واقعی، همکاری علمی و
انتشار روش تهیهٔ داده پیشنهاد می‌شود. تعداد بک‌لینک یا خرید بستهٔ لینک معیار این برنامه نیست. [G4، G5]

## ۹. برنامهٔ ۹۰روزه و مسئول هر بخش

مبدأ، روز شروع اجراست؛ تقویم انتشار قطعی و وعدهٔ رتبه نیست. مالک حساب‌ها و DNS را
انجام می‌دهد؛ توسعه‌دهنده اصلاحات و ابزارسنجی را؛ نویسنده و بازبین علمی محتوا را.

| بازه | مسئول | خروجی قابل تحویل | شرط پایان مرحله |
|---|---|---|---|
| روز ۱–۳ | مالک + توسعه‌دهنده | Search Console، شناسهٔ GA4، ثبت خط مبنا و راه‌اندازی سنجش | تأیید مالکیت و کنترل درخواست اندازه‌گیری |
| روز ۴–۱۰ | توسعه‌دهنده | اصلاح sitemap و pagination، بررسی redirect و noindex و ساختار مقاله | تست‌های رفتاری و URL Inspection صفحات نمونه |
| روز ۷–۱۴ | مالک + بازبین | معرفی حرفه‌ای محصول، دربارهٔ ما، روش بازبینی، اطلاعات نویسندگان | همهٔ ادعاها و دسترسی امکانات تأیید شوند |
| روز ۱۵–۳۰ | نویسنده + بازبین | ۴ محتوای نخست، لینک داخلی و تصاویر اختصاصی | انتشار پس از بازبینی، حضور صفحات مناسب در sitemap |
| روز ۳۱–۶۰ | تیم محتوا + توسعه‌دهنده | ۴ محتوای بعد، معرفی قابلیت‌های واقعی، اصلاح مشکلات سرعتِ اندازه‌گیری‌شده | گزارش دستگاه و query و صفحه، رویدادهای تعریف‌شده |
| روز ۶۱–۹۰ | مالک + محتوا | اصلاح صفحات دارای impression مرتبط، توسعهٔ خوشهٔ موفق و همکاری علمی | گزارش مقایسهٔ بازه‌های ۲۸روزه و تصمیم ادامه بر پایهٔ داده |

## ۱۰. سنجش نتیجه و تعریف رویدادها

| شاخص | محل اندازه‌گیری | تصمیمی که پشتیبانی می‌کند |
|---|---|---|
| خطای دسترسی/خزیدن و وضعیت canonical | URL Inspection، Page indexing، لاگ سرور | اصلاح مانع فنی |
| impressions و clicks غیربرند مرتبط | Search Console با تفکیک صفحه و دستگاه | انتخاب خوشه و موضوع بعدی |
| CTR با جایگاه مشابه | Search Console | آزمون عنوان و تناسب نیت |
| ورود به وب‌اپ از محتوای عمومی | رویداد سفارشی `open_web_app` | کیفیت CTA؛ این رویداد هنوز پیاده نشده |
| کلیک دانلود | رویداد سفارشی `download_click` | علاقه به نسخهٔ محصول؛ کلیک را نصب موفق نشمارید |
| ثبت‌نام موفق | رویداد پیشنهادی GA4 به نام `sign_up` | فقط پس از تکمیل واقعی ثبت‌نام، نیازمند ابزارسنجی سایت/اپ |
| خرید موفق | `purchase` با transaction_id یکتا | فقط پس از verify پرداخت؛ یک بار به ازای تراکنش |
| تجربهٔ موبایل | دادهٔ میدانی CWV و تست آزمایشگاهی | اولویت اصلاح تجربه [G19] |

نام رویدادهای پیشنهادی GA4 و پارامترهای لازم در مرجع رسمی کنترل شوند. [G20]
همهٔ رویدادهای جدول به‌جز page_view نمونه، نیازمند توسعه‌اند. اگر واحد پول سایت تومان
است، مقدار رویداد خرید باید به واحد استاندارد انتخابی با تبدیل درست و مستند ارسال شود.
تا پیش از دادهٔ واقعی، هدف افزایش درصدی ساختگی تعیین نکنید. پس از خط مبنای ۲۸روزه،
هدف ماه بعد برای ورودی مرتبط و ثبت‌نام/خرید واقعی تعیین شود؛ هیچ جایگاه یا زمان ایندکس تضمین نیست.

### چک‌لیست انتشار هر صفحه

- [ ] نیت اصلی و مخاطب حرفه‌ای مشخص، صفحهٔ هم‌نیت تکراری وجود ندارد.
- [ ] محتوا، نویسنده، بازبین، ارجاع و تاریخ علمی بررسی شده‌اند.
- [ ] پاسخ HTTP، عنوان، description، canonical، index policy و نمایش موبایل بررسی شده‌اند.
- [ ] تصویر و alt مناسب؛ JSON-LD معتبر و مطابق محتوای دیداری است.
- [ ] لینک داخلی ورودی و مقصد CTA وجود دارند و کار می‌کنند.
- [ ] برای صفحهٔ قابل ایندکس، sitemap و URL Inspection بررسی شده‌اند.
- [ ] اطلاعات شخصی، بیمار یا توکن در درخواست‌های تحلیل‌گر ارسال نمی‌شوند.
- [ ] تغییر و تاریخ آن در گزارش ثبت شده تا نتیجه بعداً قابل مقایسه باشد.

## ۱۱. وضعیت کار و اطلاعات لازم برای اجرا

انجام‌شده: بررسی کد، مشاهدهٔ عمومی چهار نشانی، تهیهٔ این برنامه، نقشهٔ کلمات پیشنهادی،
نمونهٔ تحلیل‌گر و پیوند راهنما در README.

گام مالک اکنون: ساخت Domain property و افزودن TXT به DNS؛ یا ساخت URL-prefix و
فرستادن مقدار content تگ صادرشده. سپس ساخت GA4 Web stream و ارائهٔ شناسهٔ عمومی `G-...`.
رمز حساب گوگل، توکن ورود، کد یک‌بارمصرف و کلید خصوصی لازم نیست و نباید ارسال شود.
این سند هیچ تأییدی از حساب گوگل یا ذخیرهٔ تنظیمات واقعی را ادعا نمی‌کند.
