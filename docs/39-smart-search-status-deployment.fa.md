**چرا انتقال به سرور هنوز فقط migrate و کپی دیتابیس نیست؟**

در `reference_index.source_stamp`، هویت SQLite به مسیر مطلق پوشه و revision به مشخصات فایل، از جمله inode و زمان تغییر وابسته است. مسیر لوکال با `/sd/uptodate` سرور فرق می‌کند. همچنین `SearchChunk.block_ids` شناسهٔ عددی ردیف‌های `ReferenceParagraph` در دیتابیس اصلی همان محیط را نگه می‌دارد؛ بازیاب آن‌ها را با `source_generation` بررسی می‌کند. بازسازی مستقل منبع در سرور ممکن است همین متن را با شناسه‌های متفاوت ذخیره کند.

در نتیجه restore صرف دیتابیس بازیابی می‌تواند با `HYBRID_INDEX_NOT_READY` یا `REFERENCE_INDEX_STALE` رد شود؛ این کنترل نباید برای عبور موقت حذف شود. restore دیتابیس اصلی لوکال روی دیتابیس کاربران سرور نیز روش مناسبی نیست. دستورهای فعلی build/clone/activate، export/import قابل‌حمل با نگاشت مقصد را انجام نمی‌دهند.

مسیر پیشنهادیِ هنوز نیازمند پیاده‌سازی:

1. از بردارهای همین نسل، بستهٔ نسخه‌دارِ `input_hash → vector` به همراه profile کامل، تعداد، checksum و metadata منبع صادر شود؛ کلید API، کاربران و jobها داخل آن نباشند.
2. روی سرور، منبع آمادهٔ فعلی ابتدا اعتبارسنجی و در صورت نیاز با `UPTODATE_DB_DIR=/sd/uptodate` بازسازی شود؛ نسل chunk مقصد شناسه‌ها و pin صحیح خود سرور را بگیرد.
3. بردارها فقط در صورت برابری دقیق `input_hash` و profile به قطعات مقصد وصل شوند. mismatch، ورودی مفقود و ابعاد نامعتبر صریحاً گزارش شوند. برای متن یکسان embedding دوباره خریداری نشود؛ اگر منبع/قطعه‌بندی فرق کرده است، میزان کار جدید پیش از درخواست پولی مشخص شود.
4. HNSW مقصد ساخته و شمارش، ارجاع‌ها، بازیابی و پاسخ واقعی کنترل شوند؛ سپس head به‌صورت اتمی تغییر کند. نگهداری یک نسل کامل سازگار و تنظیم‌های متناظر برای rollback لازم است.

انتقال منطقی PostgreSQL نیز تعریف ایندکس را بازسازی می‌کند؛ کپی dump برابر انتقال فایل فیزیکیِ HNSW آماده نیست. [مرجع PostgreSQL 17](https://www.postgresql.org/docs/17/app-pgdump.html).

**زیرساخت و تنظیم‌های استقرار**

| جزء | نیاز استقرار |
|---|---|
| دیتابیس اصلی | حفظ کاربران/اشتراک‌ها و migrationهای جدید SearchRun/منبع آماده؛ پشتیبان قبل از تغییر |
| دیتابیس بازیابی | اتصال مستقل `REFERENCE_SEARCH_DATABASE_URL`، PostgreSQL با pgvector و فضای پایدار؛ نسخهٔ سازگار افزونه برای HNSW/iterative scan |
| دیتابیس بازخورد | PostgreSQL مستقل از طریق `AI_LAB_FEEDBACK_DATABASE_URL` و migration اختصاصی |
| Redis | سرویس مشترک cache/throttle، event stream و broker، با تفکیک کلید/DB، سیاست حافظه و ظرفیت اندازه‌گیری‌شده |
| API و worker | ASGI برای اتصال استریم و Celery جدا برای `ai_search`؛ `AI_LAB_EXECUTOR=celery`، `CELERY_TASK_ALWAYS_EAGER=False` و `CELERY_RUN_TASKS_IN_REQUEST=False` |
| منابع UpToDate | mount پایدار و تنظیم `UPTODATE_DB_DIR=/sd/uptodate`، با snapshot معتبر و قابل بازسازی |
| مدل‌ها | متغیرهای محیطی مستقل chat و embedding؛ Luna/low برای پاسخ و دقیقاً small/1536/profile همین نسل برای query embedding |
| فرانت‌اند/پروکسی | انتشار client جدید دریافت NDJSON، عبور جریان بدون buffering/cache پاسخ و بررسی قطع/ادامه در دامنهٔ واقعی و اندروید |

نام متغیرهای اصلی مدل: `AI_LAB_MODEL`، `AI_LAB_BASE_URL`، `AI_LAB_API_KEY` و `AI_LAB_REASONING_EFFORT`. برای embedding: `AI_LAB_EMBEDDING_BACKEND=openai`، `AI_LAB_EMBEDDING_REMOTE_ENABLED=True`، `AI_LAB_EMBEDDING_MODEL=text-embedding-3-small`، `AI_LAB_EMBEDDING_DIMENSIONS=1536`، `AI_LAB_EMBEDDING_BASE_URL`، `AI_LAB_EMBEDDING_API_KEY`، `AI_LAB_EMBEDDING_USE_CHAT_KEY=False` و revision منطبق. کلیدها فقط در secrets سرور ذخیره شوند. `AI_LAB_LOCAL_LEXICAL_PILOT=False` برای تولید الزامی است و rollout ابتدا صفر می‌ماند. `.env.example` و پیش‌فرض کد هنوز ابعاد ۷۶۸ دارند؛ کپی کورکورانهٔ آن‌ها با این نسل ۱۵۳۶بعدی سازگار نیست و در بستهٔ انتشار باید صریحاً اصلاح/تعیین شوند.

تبدیل کل منبع UpToDate از SQLite به PostgreSQL پیش‌نیاز این معماری نیست: متن خام می‌تواند در SQLite بماند، در حالی که مسیر بازیابی آماده و برداری از PostgreSQL استفاده می‌کند. درخواست‌های تازه همچنان برای بردار سؤالِ کش‌نشده به API embedding و برای پاسخ به API مدل نیاز دارند؛ ساخت corpus به معنی حذف این اتصال‌ها نیست. GPU اختصاصی برای این مسیر API لازم نیست.

حجم فعلی **کل** دیتابیس retrieval لوکال حدود `15 GB` است و نسل‌های قدیمی/پایلوت را هم شامل می‌شود؛ جدول بردار به همراه ایندکس‌هایش حدود `11 GB`، جدول chunk به همراه ایندکس‌هایش `3536 MB` و HNSW جدید به‌تنهایی `5242 MB` است. این اعداد با هم جمع نمی‌شوند چون بعضی زیرمجموعهٔ دیگری‌اند. جدول پاراگراف آماده در دیتابیس اصلی نیز جداگانه حدود `1561 MB` و زیربخش‌ها `149 MB` هستند. ظرفیت دیسک باید علاوه بر دادهٔ فعال، WAL، ساخت/نسل بعدی و بکاپ را پوشش دهد؛ ۵ گیگابایت کل فضای موردنیاز نیست. RAM/vCPU نهایی و quota رانفلر باید با بار واقعی تأیید شوند.

در ساخت لوکال محدودیت پیش‌فرض ۶۴ MiB shared memory کانتینر روی یک query پایش اثر گذاشت؛ خود build پایان یافت. برای ساخت مقصد باید `shm_size` و حافظهٔ maintenance/parallel worker متناسب تنظیم یا ساخت سریالی انتخاب شود. [راهنمای رسمی pgvector](https://github.com/pgvector/pgvector#docker). دریافت استریم نیز باید با iterator ناهمگام زیر ASGI آزموده شود. [مرجع Django](https://docs.djangoproject.com/en/5.2/ref/request-response/#streaminghttpresponse-objects).

ترتیب عملیاتی سرور پس از تکمیل ابزار انتقال: تست و commit کد → پشتیبان → فراهم‌کردن DB/Redis/worker و secrets → deploy محدود و migrationها → ساخت/اعتبارسنجی منبع مقصد و import بردار → ساخت HNSW → آزمون runtime/منابع/کیفیت/سرعت → activate و انتشار تدریجی فرانت‌اند/قابلیت. migrationهای موجود عبارت‌اند از:

```bash
python manage.py migrate
python manage.py migrate --database reference_search
python manage.py migrate ai_feedback --database ai_feedback
```

این سه دستور schema را آماده می‌کنند و بردارها را منتقل نمی‌کنند. `python manage.py check_search_runtime` آزمون worker/Redis بدون فراخوانی مدل دارد. فرمان import بردار مقصد هنوز وجود ندارد؛ بنابراین این گزارش، برنامهٔ استقرار است و هنوز دستور نهاییِ آمادهٔ انتقال کل نسل محسوب نمی‌شود.
