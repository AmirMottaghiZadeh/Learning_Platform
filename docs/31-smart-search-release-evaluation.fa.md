# فاز پنج سرچ هوشمند: ارزیابی کامل و شرط انتشار

تاریخ: ۲۰۲۶/۱۱/۱۱. ابزارهای این فاز پیاده‌سازی و آزمون واقعی اجرا شدند، اما **هدف پاسخ کامل و تأییدشده برای حداقل ۹۵٪ سؤال‌های پزشکی در کمتر از ۲۰ ثانیه محقق نشده است**. تصمیم فعلی `blocked` است؛ انتشار عمومی فعال نشده و فایل مجوز انتشار ساخته نشده است. مالک پروژه بازبینی بالینی را انجام می‌دهد. سرچ معمول اپ و tagging آن تغییر نکرده و بردارسازی اضافه نشده است.

## نتیجهٔ اندازه‌گیری

[گزارش عددی قابل ثبت در مخزن](search/evaluation/phase5-release-2026-11-11.json) متن پاسخ، نقل‌قول، کلید و شناسهٔ حساب ندارد. گزارش کامل و برگهٔ بازبینی فقط در `backend/exports/phase5-2026-11-11/`، بیرون از Git و Docker، ذخیره شده‌اند؛ مجوز پوشه `700` و فایل‌ها `600` است.

| مسیر واقعی | تعداد نمونه | پاسخ کامل ماشینی | p50 پاسخ‌های کامل | p95 پاسخ‌های کامل |
|---|---:|---:|---:|---:|
| سرویس، همهٔ سؤال‌های پزشکی | ۹۵ | ۶۳، معادل ۶۶٫۳٪ | ۱۰٫۴۱ ثانیه | ۱۵٫۹۵ ثانیه |
| HTTP همراه احراز هویت، پذیرش و polling، cold | ۲۰ | ۱۴ | ۱۰٫۵۸ ثانیه | ۱۷٫۷۵ ثانیه |
| HTTP، تکرار همان سؤال حساب | ۱۴ | ۱۳ | ۰٫۱۰ ثانیه | ۱٫۲۹ ثانیه |
| نمایش در Chrome، cold | ۱۰ | ۷ | ۱۲٫۵۴ ثانیه | ۱۵٫۶۱ ثانیه |
| نمایش در Chrome، hit و موارد skipped | ۱۰ | ۷ | ۱٫۱۸ ثانیه | ۱٫۱۹ ثانیه |

صدک‌ها فقط از پاسخ‌های کامل محاسبه می‌شوند؛ خطا و partial از مخرج نرخ موفقیت حذف نشده‌اند. در مجموعهٔ پزشکی، ۲۷ timeout و پنج پایان کار با پاسخ ناقص وجود داشت. پنج سؤال غیرپزشکی نیز بدون پاسخ پزشکی خاتمه یافتند. تمام ۶۳ پاسخ کامل از کنترل فنی نقل‌قول و مقصد گذشتند؛ ۴۰ پاسخ با مقاله و بخش مرجع آزمون تطبیق داشتند و ۲۳ مورد نیازمند بررسی منبع جایگزین هستند. این اعداد تأیید بالینی نیستند؛ بازبینی هر ۱۰۰ مورد اصلی هنوز pending است.

آزمون HTTP از API واقعی با دو worker گانیکورن، هم‌زمانی دو و Redis مشترک و جداگانهٔ تشخیصی عبور کرد؛ محدودیت حساب و نرخ درخواست دور زده نشد. شش cold timeout و یک hit با خطای احراز هویت در نتیجه باقی مانده‌اند. دو جفت cold/hit که به علت اجرای قبلی کش داشتند، با حساب‌های تازه و همان runtime دوباره اندازه‌گیری شدند؛ اصل گزارش و جایگزین‌ها برای ردیابی نگه‌داری شده‌اند. ابزار اکنون cold کش‌شده را موفقیت حساب نمی‌کند. خطای اولیهٔ ابزار در خواندن HTTP 202 نیز اصلاح و با تست پوشش داده شد؛ اجرای مخدوش اولیه وارد امتیاز نهایی نشده است.

در مرورگر، سه hit به علت نبود پاسخ کامل cold اجرا نشدند و skipped هستند؛ هفت hit واقعی همگی پاسخ کامل نمایش دادند. در یک cold، job تمام شد ولی پاسخ partial بود و موفقیت نمایش کامل محسوب نشد. زمان حدود ۱٫۲ ثانیهٔ hit در رابط با زمان حدود میلی‌ثانیه‌ای سرویس در فاز چهار متفاوت است؛ polling و رندر جزو اندازه‌گیری مرورگر هستند. این آزمون Chrome لوکال است و تضمین عملکرد اپ اندروید یا شبکهٔ کاربران نیست.

اجرای اولیه پس از ۹۵ مورد به سقف ۴۰۰ درخواست provider رسید. فقط مورد قطع‌شده با بودجه و پنج سؤال باقی‌مانده در اجرای تکمیلی انجام شدند؛ شکست‌های زمانی برای بهتر شدن امتیاز تکرار نشدند. مجموع این دو اجرا ۴۱۰ درخواست provider است؛ ۱۰۰ سطر انتخاب‌شده ۴۰۷ درخواست و ۳۴۳۱۲۱ توکن شناخته‌شده دارند. usage بعضی درخواست‌ها نامعلوم است و تلاش جایگزین‌شده نیز در این جمع توکن نیست؛ این عدد صورتحساب کل نیست. ترافیک HTTP و مرورگر مصرف جدا دارد.

## بازبینی توسط مالک پروژه

فایل خصوصی `backend/exports/phase5-2026-11-11/review.html` را در مرورگر باز کنید. ۱۳۳ جفت یکتای سؤال/پاسخ از مجموعهٔ اصلی، بار HTTP و مرورگر در آن وجود دارد. پاسخ‌های بالینی یکسان با تنظیم یکسان فقط یک بار بررسی می‌شوند؛ تغییرات زمان و کش نظر قبلی را باطل نمی‌کنند. متن توضیح اصلی فارسی، خلاصهٔ فارسی ارجاع، نقل‌قول اصلی، مقصد و بخش مرجع آزمون نمایش داده می‌شوند.

۱. نام خود را وارد کنید و برای هر پاسخ «کافی و درست» یا «نیازمند اصلاح / پاسخ ناکافی» را انتخاب کنید. موارد بررسی‌نشده را می‌توان pending گذاشت.
۲. اگر مقاله یا بخش متفاوت واقعاً پاسخ را پوشش می‌دهد، پذیرش منبع جایگزین را مشخص کنید و دلیل حداقل ۱۵ نویسه‌ای بنویسید. این نظر، نقل‌قول نامعتبر، پاسخ ناقص یا زمان بیش از حد را قابل قبول نمی‌کند.
۳. «دریافت فایل نظرها» یک JSON شامل نظرهای صریح می‌سازد. فایل را در مسیر خصوصی با مجوز `600` نگه دارید. با وارد کردن همین فایل می‌توان بازبینی را ادامه داد؛ ذخیرهٔ خودکار بین بستن مرورگر وجود ندارد.

کاربرگ کاملاً آفلاین است، درخواست شبکه ندارد و هیچ نظر مثبتی از قبل انتخاب نشده است. نظرها به شناسهٔ سؤال، hash پاسخ، پیکربندی مدل و منبع وابسته‌اند. ویرایش متن پاسخ، overview فارسی، نقل‌قول یا منبع، نظر قبلی را معتبر نگه نمی‌دارد. کنترل مجدد source binding در زمان گیت انجام می‌شود؛ فایل نظرها جایگزین صحت‌سنجی منبع نیست.

برای بازتولید کاربرگ، از `backend/` و با تنظیم محیط متناظر گزارش اجرا کنید؛ نام خروجی باید تازه باشد:

```bash
python manage.py review_reference_release \
  --input exports/phase5-2026-11-11/suite.json \
  --input exports/phase5-2026-11-11/http-load.json \
  --input exports/phase5-2026-11-11/browser.json \
  --output exports/review-next.html
```

## سنجش از مسیر واقعی

[benchmark_reference_http](../backend/apps/ai_lab/management/commands/benchmark_reference_http.py) به یک API مشخص، درخواست عادی `ask` و polling نتیجه می‌فرستد. فایل حساب‌ها باید خصوصی با مجوز `600`، دارای `schema: 1` و آرایهٔ `accounts` با `access_token`های نشست واقعی `phx_access_...` باشد. از حساب‌های اختصاصی آزمون که با روش معمول وارد شده‌اند و مجوز سرچ هوشمند دارند استفاده کنید؛ حساب‌های staff برای تشخیص worker لازم‌اند. کلید مدل در این فایل نیست. برای ۲۰ سؤال با هم‌زمانی دو، حداقل چهار حساب تازه فراهم کنید تا گروه‌های هشت‌سؤالی از محدودیت ۲۰ جست‌وجو در ساعت عبور نکنند؛ نشست‌ها باید در طول آزمون اعتبار داشته باشند.

```bash
python manage.py benchmark_reference_http \
  --accounts-file /private/reference-accounts.json \
  --api-base http://127.0.0.1:8765/api/v1 \
  --limit 20 --concurrency 2 --poll 1 --max-requests 120 \
  --output exports/http-load-next.json
```

API هدف و محیط اجرای فرمان باید از نظر مدل، منبع، نسل و تنظیم runtime یکسان باشند؛ preflight پیش از مصرف API این تطبیق را کنترل می‌کند. سقف `--max-requests` تمام تلاش‌های هر سؤال را رزرو می‌کند و برای مصرف نامعلوم، کل رزرو را مصرف‌شده حساب می‌کند. پاسخ‌های موجود کش را پاک نمی‌کند؛ برای cold از حساب‌های تازه استفاده کنید. HTTP غیررمزشده فقط روی loopback مجاز است؛ در محیط دیگر HTTPS لازم است. redirect حامل توکن دنبال نمی‌شود.

برای سنجش رابط وب، export را با API تشخیصی بسازید، آن را فقط روی loopback سرو کنید و از `frontend/` اجرا کنید. این اسکریپت فقط localhost را قبول می‌کند؛ Chrome باید نصب باشد. فایل حساب مرورگر علاوه بر access، به `refresh_token` و `session_id` نشست واقعی نیاز دارد. یک حساب تازهٔ جدا برای حداکثر ۱۰ جفت استفاده کنید تا با سقف ساعتی تداخل نکند.

```bash
npm run benchmark:reference-browser -- \
  --accounts=/private/reference-accounts.json \
  --app=http://127.0.0.1:8766/ \
  --api=http://127.0.0.1:8765/api/v1 \
  --limit=10 --max-requests=72 \
  --output=/private/browser-raw-next.json
```

اسکریپت Chrome با پروفایل موقت جدا، ورود معمول و خود فرم اپ کار می‌کند. نتیجهٔ terminal API و زمان `performance.measure` پس از دو animation frame و وجود واقعی ارجاع در پاسخ کامل ثبت می‌شوند. نمایش عنوان یا اولین ارجاع، پایان پاسخ کامل محسوب نمی‌شود. نام‌های measure عبارت‌اند از `pharmenta.reference.titles`، `first_citation` و `finished`. detail فقط شناسهٔ تصادفی نوبت، زمان و وضعیت دارد؛ متن سؤال یا توکن ثبت نمی‌شود. بازیابی job قدیمی، زمان شروع تازهٔ ساختگی ندارد. پروفایل موقت مرورگر پس از اجرا حذف می‌شود.

از `backend/` خروجی خام را به گزارش متصل به منبع تبدیل کنید؛ این فرمان مصرف مدل ندارد:

```bash
python manage.py collect_reference_browser \
  --input /private/browser-raw-next.json \
  --output exports/browser-next.json
```

SHA-256 فایل اصلی JS که واقعاً سرو شده همراه اندازه‌گیری ثبت می‌شود. گیت آن را با `AI_LAB_FRONTEND_BUNDLE_SHA256` یا export موجود لوکال مقایسه می‌کند. export تشخیصی این اندازه‌گیری به API موقت اشاره داشت؛ پس از آزمون، export معمول لوکال بازسازی می‌شود. برای انتشار واقعی باید build و API همان محیط اندازه‌گیری شوند؛ گزارش لوکال مجوز انتشار روی سرور دیگری نیست.

## گیت انتشار و rollout

[release.py](../backend/apps/ai_lab/release.py) فقط با تمام شرایط زیر `pass` می‌دهد:

- تمام ۱۰۰ سؤال مجموعه دقیقاً یک بار در گزارش اصلی حاضر باشند؛ تمامشان نظر مستقل صریح داشته باشند و امتناع‌های غیرپزشکی نیز تأیید شوند.
- حداقل ۹۵٪ سؤال‌های پزشکی، پاسخ کامل، ارجاع معتبر، منبع مورد انتظار یا جایگزین مستدل، تأیید بالینی و زمان سخت‌گیرانهٔ `<20000ms` داشته باشند. پاسخ کش‌شده جای cold مجموعهٔ اصلی را نمی‌گیرد.
- در HTTP حداقل ۲۰ cold و ۲۰ hit یکتا و در مرورگر حداقل ۱۰ cold و ۱۰ hit یکتا وجود داشته باشد؛ در هر گروه حداقل ۹۵٪ موفقیت تأییدشده زیر ۲۰ ثانیه لازم است. hit باید واقعاً از کش و با صفر درخواست provider باشد. partial، خطای سریع، رد دسترسی و skipped موفقیت نیستند.
- آزمون HTTP به ظرفیت هم‌زمان پیکربندی‌شده برسد و دست‌کم دو worker با Redis مشترک مشاهده شده باشند. نسل آمادهٔ معتبر، پیکربندی runtime، منبع، کد مسیر پاسخ و build وب با شواهد منطبق باشند.

```bash
python manage.py evaluate_reference_release \
  --suite exports/phase5-2026-11-11/suite.json \
  --load exports/phase5-2026-11-11/http-load.json \
  --browser exports/phase5-2026-11-11/browser.json \
  --reviews /private/reference-reviews.json \
  --output exports/release-gate-next.json
```

خروجی حتی در حالت blocked با دلایل نوشته می‌شود؛ تصمیم و `release_slo_verified` را بخوانید. درخواست ساخت مجوز با `--approval-output /private/reference-approval.json --expires-hours 24` فقط پس از `pass` پذیرفته می‌شود. این فایل با `SECRET_KEY` همان محیط امضا می‌شود، به runtime و build وب وابسته است، حداکثر ۷۲ ساعت اعتبار دارد و باید مجوز `600` داشته باشد. کپی فایل به محیط دارای SECRET_KEY، منبع یا build متفاوت مجوز معتبر نمی‌سازد. تغییر runtime حداکثر با تأخیر ۱۰ ثانیه‌ای بررسی مجدد می‌شود؛ انقضا در هر خواندن کنترل می‌شود.

| متغیر | پیش‌فرض و اثر |
|---|---|
| `AI_LAB_MAX_CONCURRENT_JOBS` | `2`؛ جایگاه‌های مشترک و اندازهٔ executor؛ محدودهٔ عملیاتی ۱ تا ۱۶ |
| `AI_LAB_ROLLOUT_PERCENT` | `0`؛ درصد cohort عمومی؛ بدون مجوز معتبر، درصد مثبت هم دسترسی جدید نمی‌دهد |
| `AI_LAB_RELEASE_APPROVAL_FILE` | خالی؛ مسیر خصوصی مجوز امضاشده و معتبر |
| `AI_LAB_FRONTEND_BUNDLE_SHA256` | خالی؛ hash فایل اصلی JS اندازه‌گیری‌شده؛ در بک‌اند بدون `frontend/dist` باید تنظیم شود |

`AI_LAB_ENABLED` همچنان کلید اصلی روشن/خاموش است. مدیران و `AI_LAB_USER_IDS` دسترسی آزمایشی قبلی را دارند؛ cohort عمومی فقط با مجوز معتبر اضافه می‌شود. پس از تأیید واقعی، rollout دستی ۰ ← ۵ ← ۲۵ ← ۱۰۰ با همان تقسیم‌بندی ثابت HMAC حساب انجام می‌شود؛ افزایش درصد کاربران مرحلهٔ قبل را خارج نمی‌کند. هر مرحله نیازمند مشاهدهٔ خطا، timeout، کیفیت و زمان واقعی است. بازگشت درصد به صفر، مسیر عمومی cohort را می‌بندد؛ نشست‌های آزمایشی صریح همچنان تابع مجوز خود هستند. rollout خودکار یا تغییر تنظیم سرور در این فاز انجام نشده است.

`GET /api/v1/ai-lab/status/?diagnostics=1` فقط برای staff، شناسهٔ تصادفی worker، hash پیکربندی، ظرفیت و backend کش job/پاسخ را اضافه می‌کند. صفحهٔ کاربر اطلاعات مدل یا این تشخیص‌ها را نمایش نمی‌دهد.

## بررسی فنی و ادامهٔ کار

۳۰۳ تست بک‌اند ai_lab، activity، uptodate، offline و lexicomp موفق شدند؛ تست‌های گیت پس از اصلاح نهایی نیز جداگانه اجرا شدند. سه تست زمان رندر، آزمون واقعی کاربرگ در Chrome (۱۳۳ مورد، خروجی خالی برای pending و اتصال نظر صریح به hash پاسخ)، TypeScript و export وب موفق‌اند و `makemigrations --check --dry-run` تغییری نشان نداد. اعتبار hash پاسخ، باطل شدن نظر حذف‌شده، بررسی source جایگزین، فراردهی HTML، 202 واقعی، نبود شواهد/worker، partial، مرز دقیق ۲۰ ثانیه، build نامنطبق و امضای مجوز پوشش داده شده‌اند.

نتیجهٔ عملی این فاز، قابل اندازه‌گیری شدن شکست‌ها و جلوگیری از اعلام موفقیت کاذب است. برای رسیدن به هدف باید timeoutهای سؤال تازه، شکست تمام پنج سؤال چندبخشی و انتخاب بخش‌های مرجع با استفاده از گزارش هر مرحله اصلاح شوند؛ بازبینی شما مشخص می‌کند کدام پاسخ‌های موجود از نظر بالینی کافی هستند. پیش از رفع این موارد و تکرار آزمون‌ها، مجوز rollout صادر نمی‌شود.
