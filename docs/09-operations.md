## مانیتورینگ

### مسیرهای سلامت

| مسیر | چه چیزی را می‌سنجد | کاربرد |
|---|---|---|
| `https://api.pharmenta.ir/api/v1/live/` | فقط زنده بودن پروسه | health check کانتینر |
| `https://api.pharmenta.ir/api/v1/health/` | پروسه و دیتابیس | health check رانفلر |
| `https://api.pharmenta.ir/api/v1/ready/` | دیتابیس و کش (و صف، اگر لازم باشد) با تأخیر هر کدام | **پایش بیرونی**؛ 503 یعنی سرویس مشکل دارد |
| `https://app.pharmenta.ir/` | سرو وب‌اپ | پایش بیرونی |
| `https://pharmenta.ir/` | سایت | پایش بیرونی |

```bash
curl -s https://api.pharmenta.ir/api/v1/ready/
# {"status":"ok", …, "checks":{"database":"ok","database_latency_ms":…,"cache":"ok",…}}
```

### پایش پیشنهادی

1. یک سرویس پایش uptime که به سرورهای داخل ایران دسترسی دارد، هر ۱ تا ۵ دقیقه این سه نشانی را بررسی کند: `/api/v1/ready/` (انتظار: 200 و `"status":"ok"`)، `https://app.pharmenta.ir/` و `https://pharmenta.ir/`.
2. هشدار به ایمیل یا پیام‌رسان فرستاده شود.
3. انقضای گواهی SSL هر سه دامنه و `s3-pish.runflare.cloud` هم پایش شود.

### لاگ‌ها

لاگ‌ها در خروجی استاندارد کانتینر نوشته می‌شوند و در پنل رانفلر، بخش لاگ هر سرویس، دیده می‌شوند. production همه را JSON می‌نویسد.

| منبع | شکل | محتوا |
|---|---|---|
| Gunicorn (هر درخواست) | `{"timestamp","level","event":"http_request","request_id","method","path","status","duration_us","remote_addr"}` | همهٔ درخواست‌ها با زمان پاسخ |
| Django و اپ‌ها | JSON با `request_id` | خطاها و هشدارهای اپ‌ها (`apps.*`) و `django.request` |
| `docker-start.sh` | `[docker-start] >>> <قدم>` و `!!! FAILED (exit N)` | شروع کانتینر |

**ردگیری یک خطا:** هر پاسخ API هدر `X-Request-ID` دارد. همان مقدار را در لاگ رانفلر جست‌وجو کنید تا همهٔ لاگ‌های آن درخواست پیدا شوند.

سطرهای مهم:

| سطر لاگ | معنی |
|---|---|
| `sms.ir rejected the code for …: HTTP <کد> <پیام>` | sms.ir درخواست را رد کرد: کلید، قالب، اعتبار پنل یا محدودیت IP |
| `sms.ir unreachable for …` | ارتباط با sms.ir برقرار نشد |
| `sms.ir refused the code for …` | sms.ir پاسخ داد ولی وضعیتش موفق نبود |
| `SMS (console backend, not sent)` | `SMSIR_API_KEY` تنظیم نیست و هیچ پیامکی فرستاده نمی‌شود |
| `[docker-start] !!! FAILED` | یکی از قدم‌های شروع شکست خورد؛ سطر قبلش قدم را نشان می‌دهد |

## بکاپ و بازیابی

### چه چیزی باید بکاپ شود

| داده | بازسازی‌پذیر؟ | بکاپ |
|---|---|---|
| Postgres (کاربران، پرداخت‌ها، پیشرفت، سایت و رسانه‌اش، کنسول) | **خیر** | روزانه با `backup_database` |
| MySQL UpToDate | بله، از SQLite منبع | بکاپ پوشهٔ SQLite منبع کافی است |
| Lexicomp روی دیسک | بله، از فایل منبع | بکاپ پوشهٔ منبع کافی است |
| بسته‌های آفلاین در باکت | بله، با `build_offline_package` و همان `OFFLINE_PACKAGE_SECRET` | نیاز ندارد؛ فقط راز را نگه دارید |
| پایپلاین‌ها و دادهٔ منبع روی لپ‌تاپ (`openfda/`، `UpToDate/`، `Lexicomp_Drug_Interactions/`، `Medscape/`، `pharmenta-reference-data/`) | **دشوار** (ساعت‌ها تا روزها کار) | یک نسخه روی دیسک یا فضای ابری جدا |
| `backend/.env` لپ‌تاپ و env رانفلر | — | در گذرواژه‌نگار (پایین‌تر) |

### گرفتن بکاپ

`backup_database` با `pg_dump` (قالب custom) یک فایل تاریخ‌دار می‌سازد و هیچ داده‌ای را تغییر نمی‌دهد. نسخهٔ `pg_dump` لپ‌تاپ باید هم‌نسخهٔ Postgres سرور یا تازه‌تر باشد.

از لپ‌تاپ با رشتهٔ اتصال **خارجی** Postgres رانفلر:

```bash
cd backend
DATABASE_URL="postgresql://<user>:<رمز>@<host خارجی>:<port>/<db>?sslmode=require" \
  .venv/bin/python manage.py backup_database --output-dir ~/pharmenta-backups --name runflare
# → ~/pharmenta-backups/runflare-YYYYMMDD-HHMMSS.dump
```

| گزینه | پیش‌فرض | کار |
|---|---|---|
| `--output-dir` | `backend/backups` | پوشهٔ خروجی |
| `--name` | `database` | پیشوند نام فایل |
| `--dry-run` | — | فقط مسیر را چاپ می‌کند |

برنامهٔ پیشنهادی:
- **روزانه:** یک بکاپ بگیرید. می‌توانید با cron روی لپ‌تاپ یا هر ماشین همیشه‌روشن خودکارش کنید و رشتهٔ اتصال را در فایل env همان ماشین با دسترسی محدود (`chmod 600`) نگه دارید.
- **نگهداری:** ۷ بکاپ روزانهٔ آخر و ۴ بکاپ هفتگی آخر را نگه دارید.
- **نسخهٔ دوم:** یک نسخه از بکاپ‌ها جای دیگری باشد، مثلاً یک باکت خصوصی دیگر یا دیسک بیرونی.
- **پیش از کار پرخطر:** همیشه یک بکاپ دستی بگیرید؛ یعنی پیش از `--prune`، ایمپورت جایگزین‌کننده، مایگریشن حذف‌کننده یا `reset_runflare_db.sh`.

### بازیابی

بازیابی دادهٔ مقصد را **پاک و جایگزین** می‌کند.

```bash
pg_restore --clean --if-exists --no-owner -d "<DATABASE_URL مقصد>" ~/pharmenta-backups/runflare-20261023-120000.dump
```

- **آزمون منظم:** هر ماه یک بکاپ را روی یک دیتابیس محلی آزمایشی برگردانید و اپ را با آن بالا بیاورید. بکاپی که هرگز آزموده نشده، بکاپ مطمئنی نیست.
- **بعد از بازیابی روی سرور:** سرویس بک‌اند را ری‌استارت کنید؛ `migrate` در شروع کانتینر هر مایگریشن جاافتاده را اجرا می‌کند.

## رازها و چیزهایی که باید امن نگه داشته شوند

مقدار هیچ‌کدام در مخزن، مستندات، چت یا تیکت نوشته نمی‌شود. جای امن پیشنهادی یک گذرواژه‌نگار (مثل Bitwarden یا KeePassXC) است که مقدار هر مورد را با تاریخ آخرین تغییر نگه دارد.

### رازهای فنی

| راز | کجا استفاده می‌شود | اگر عوض شود یا لو برود |
|---|---|---|
| `SECRET_KEY` | env بک‌اند | نشست‌های سایت و پنل، لینک‌های بازیابی و کدهای پیامکی در جریان باطل می‌شوند و آمار بازدیدکنندهٔ یکتا از نو شروع می‌شود. توکن‌های اپ باطل نمی‌شوند |
| `OFFLINE_PACKAGE_SECRET` | env بک‌اند + `.env` لپ‌تاپ | **هرگز عوض نشود.** با عوض شدن، همهٔ بسته‌های دانلودشده بی‌استفاده می‌شوند و باید بسته‌ها از نو ساخته و دانلود شوند. اگر گم شود، همین اتفاق می‌افتد |
| رمز Postgres (`DATABASE_URL`) | env بک‌اند؛ رشتهٔ خارجی برای لپ‌تاپ | دسترسی کامل به همهٔ داده‌ها |
| رمز MySQL (`UPTODATE_MYSQL_URL`) | env بک‌اند، لپ‌تاپ هنگام کپی | — |
| `SMSIR_API_KEY` | env بک‌اند | ارسال پیامک به هزینهٔ شما |
| `OFFLINE_S3_ACCESS_KEY_ID` / `OFFLINE_S3_SECRET_ACCESS_KEY` | env بک‌اند + `.env` لپ‌تاپ | دسترسی به باکت |
| شناسهٔ پذیرندهٔ درگاه‌ها | کنسول فروش یا env | — |
| `EMAIL_HOST_PASSWORD` | env بک‌اند (اگر SMTP فعال است) | — |
| رمز حساب‌های superuser | — | دسترسی به کنسول فروش، پنل و ادمین |
| کلید امضای اندروید (keystore) | EAS | **بدون آن نمی‌شود به‌روزرسانی اپ را در بازار و مایکت منتشر کرد.** با `eas credentials` نسخهٔ پشتیبان بگیرید |

### حساب‌های سرویس

دسترسی (نام کاربری، رمز، کدهای بازیابی ورود دومرحله‌ای) به همهٔ این‌ها باید در گذرواژه‌نگار باشد:

رانفلر، GitHub (مخزن `AmirMottaghiZadeh/Learning_Platform`)، Expo/EAS، sms.ir، پنل درگاه‌های پرداخت، بازار، مایکت، اینماد، ثبت‌کنندهٔ دامنهٔ `pharmenta.ir`، و در صورت استفاده Google Analytics / Search Console.

## عیب‌یابی

| نشانه | علت‌های محتمل | بررسی و رفع |
|---|---|---|
| کانتینر بک‌اند مدام ری‌استارت می‌شود | متغیر لازم نیست؛ `SECRET_KEY` ضعیف (`ImproperlyConfigured`)؛ کش per-process در production؛ دیتابیس در دسترس نیست؛ مایگریشن شکست خورده؛ MySQL برای `ensure_uptodate_search_index` در دسترس نیست یا دسترسی `ALTER` ندارد | آخرین سطرهای `[docker-start]` در لاگ |
| ثبت‌نام: `503 SMS_SEND_FAILED` | کلید یا قالب sms.ir، اعتبار تمام‌شده، محدودیت IP | سطر `sms.ir rejected …` در لاگ؛ پنل sms.ir |
| کد پیامکی در Chrome اندروید خودکار پر نمی‌شود | آخرین خط پیامک باید دقیقاً `@app.pharmenta.ir #12345` باشد؛ روی گوشی: تنظیمات ← Google ← All services ← Verification codes by SMS (هر دو گزینه روشن) و Chrome به‌عنوان مرورگر پیش‌فرض؛ شمارهٔ فرستنده نباید در مخاطبین باشد | — |
| ورود در وب‌اپ با خطای CORS | وب‌اپ روی `http` باز شده؛ `CORS_ALLOWED_ORIGINS` نادرست | nginx وب‌اپ `http` را به `https` هدایت می‌کند؛ مقدار env را بررسی کنید (بدون اسلش آخر) |
| همه‌جا `402 PREMIUM_REQUIRED` | اعمال فروش روشن است ولی پلن رایگان تعریف نشده یا ویژگی‌ها را ندارد | کنسول ← پلن‌ها؛ یا خاموش کردن اعمال در «درگاه پرداخت» |
| پرداخت ناموفق یا برنگشتن از درگاه | شناسهٔ پذیرنده، نشانی بازگشت، IP خروجی ثبت‌نشده در درگاه | کنسول ← درگاه پرداخت ← «آزمون اتصال» و «IP خروجی» |
| UpToDate: `503 FEATURE_NOT_AVAILABLE` | `UPTODATE_MYSQL_URL` نادرست یا MySQL در دسترس نیست | لاگ؛ اتصال MySQL |
| Lexicomp: `503` | `interact.db` یا `info.json` در `LEXICOMP_DB_DIR` نیست | فایل‌ها روی دیسک سرویس |
| دکمهٔ دانلود آفلاین دیده نمی‌شود | `latest.json` آپلود نشده؛ کش ۵ دقیقه‌ای سرور؛ متغیرهای `OFFLINE_S3_*` | `/api/v1/offline/packages/` با توکن یک کاربر |
| دانلود آفلاین خطای «آسیب‌دیده» | `OFFLINE_PACKAGE_SECRET` لپ‌تاپ و سرور فرق دارد؛ قطعه ناقص آپلود شده | اسکریپت «بررسی کامل بودن آپلود» در [07-data.md](07-data.md#بررسی-کامل-بودن-آپلود) |
| دانلود آفلاین در وب شکست می‌خورد ولی در اپ نه | CORS باکت | `offline_bucket_cors --show` |
| دانلود آفلاین با خطای SSL | گواهی دامنهٔ Object Storage معتبر نیست (مثلاً دامنهٔ اختصاصی با گواهی موقت `cert-manager.local`) | `OFFLINE_S3_ENDPOINT_URL` را روی `https://s3-pish.runflare.cloud` نگه دارید |
| دامنهٔ تازه خطای SSL می‌دهد | رانفلر هنوز گواهی Let's Encrypt را صادر نکرده و گواهی موقت `cert-manager.local` سرو می‌شود | `echo \| openssl s_client -connect <دامنه>:443 -servername <دامنه> \| openssl x509 -noout -issuer`؛ اگر چند ساعت ماند، پشتیبانی رانفلر |
| وب‌اپ بعد از دیپلوی نسخهٔ قدیمی را نشان می‌دهد | `deploy-web` به‌روز نشده؛ Service Worker | [08-deployment.md](08-deployment.md)، بخش «وب‌اپ»؛ یک بار بارگذاری مجدد صفحه نسخهٔ تازه را می‌آورد |
| کندی یا مصرف زیاد حافظهٔ بک‌اند | تعداد worker زیاد (CPU میزبان شمرده می‌شود) | `WEB_CONCURRENCY` را صریح بگذارید |

## کارهای دوره‌ای

| دوره | کار |
|---|---|
| روزانه | بکاپ Postgres (وقتی خودکار شد، فقط بررسی موفق بودنش) |

| سالانه | تمدید دامنه؛ بازبینی دسترسی کارکنان در پنل و کنسول |
