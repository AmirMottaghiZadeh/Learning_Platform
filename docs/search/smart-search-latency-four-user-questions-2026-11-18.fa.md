# تحلیل زمان چهار سؤال جدید مالک

تاریخ: ۲۰۲۶-۱۱-۱۸. این اجرا مستقل از پنج سرچ قبلی است. چهار سؤال جدید مالک با متن همان درخواست و با API واقعی chat و embedding اجرا شدند؛ فقط نشانه‌های نمایشی جهت متن پیرامون NSAID وارد سؤال نشدند. [دادهٔ عددی، فراخوانی‌ها و طرح SQL](smart-search-latency-four-user-questions-2026-11-18.json).

به‌روزرسانی تفسیر در همان تاریخ: [جمع‌بندی مشکلات پیاده‌سازی](smart-search-implementation-latency-issues-2026-11-18.fa.md) و [نتیجهٔ ۴۰ درخواست API](provider-latency-40-requests-2026-11-18.fa.md) مکمل این گزارش‌اند. سهم ۷۰٫۶درصدی تماس‌های مدل، جمع ۱۵ فراخوانی در زنجیرهٔ سریالی اپ است؛ این عدد به‌تنهایی اثبات نمی‌کند علت اصلی کندی، ارائه‌دهنده یا خود مدل است. تعداد تماس‌ها، SQLهای کند و ترتیب تولید/بازبینی، اولویت اصلاح و سنجش پیاده‌سازی‌اند. داده‌های این اجرا تغییر نکرده‌اند و اصلاح کد هنوز انجام نشده است.

## روش و محدودهٔ اعتبار

- موتور واقعی `services.answer → answer_hybrid`، مدل `gpt-6-luna` با reasoning برابر `none` و ارائه‌دهندهٔ معرفی‌شدهٔ مالک. embedding مستقل `text-embedding-3-small/1536` و revision برابر `1`.
- نسل برداری محلی آماده: `73f89df9-d447-4cb7-a32c-f8296b81fa4b`. دیتابیس اصلی و دیتابیس retrieval هر دو PostgreSQL محلی بودند.
- اجرای متوالی در فضای حساب تشخیصی تازه. هر چهار پاسخ `response_cache=miss` بودند؛ page cache و کش مشترک پیوندهای منبع سردسازی نشدند. کلیدها تنها در پردازهٔ تشخیصی استفاده شدند؛ فایل موقت کلید پس از خواندن حذف شد.
- پاسخ مدل، بازیابی، ابزارها و تأیید واقعی بودند. wrapperها زمان‌گیری عبوری داشتند و پاسخ یا الگوریتم را جایگزین نکردند. هیچ درخواست تکراری برای بهبود عدد زمان ارسال نشد.
- زمان SQL در thread اصلی و thread معنایی، اتصال PostgreSQL، هدر و بدنهٔ HTTP، اولین SSE، اولین متن خام، اولین callback قابل انتشار، هر دور بازیابی و بازبینی ثبت شد.
- زمان اولین متن در این گزارش، callback موتور به مسیر انتشار است؛ زمان paint موبایل یا مرورگر نیست. HTTP اپ، پذیرش/صورتحساب، صف Celery، Redis مربوط به هر قطعه، پراکسی رانفلر و دستگاه اندازه‌گیری نشدند. concurrency چهار در اجرای متوالی موتور به کار نمی‌رود.
- سقف تشخیصی هر سؤال ۱۲ تماس خارجی و ۳۰۰ ثانیه بود؛ به سقف نرسیدیم. timeout شبکهٔ برنامه ۹۰ ثانیه، سقف جست‌وجو سه دور و سقف شاهد مدل ۶۰۰۰ توکن باقی ماندند.

## انتظار پیش از شروع پاسخ HTTP مدل

ترتیب بخش‌ها رتبه‌بندی علت‌های ریشه‌ای نیست. زمان تماس‌های مدل هم از رفتار API و هم از تعداد و ترتیب فراخوانی‌هایی اثر می‌گیرد که پیاده‌سازی اپ تعیین می‌کند.

از ۱۰۳٫۰۴ ثانیهٔ تماس‌های chat، **۹۰٫۵۹ ثانیه** پیش از دریافت هدر و **۱۲٫۴۵ ثانیه** پس از دریافت هدر گذشت. بنابراین عمدهٔ زمان مدل در این نمونه‌ها پیش از شروع جریان قابل خواندن بود، نه نوشتن آهستهٔ متن در فرانت‌اند.

این زمان ترکیبی از مسیر شبکه، gateway، صف احتمالی ارائه‌دهنده و پردازش پیش از هدر است. دسترسی داخلی به ارائه‌دهنده نداریم؛ سهم این اجزا از هم جدا نشده و نباید تمام آن «thinking» نامیده شود. reasoning درخواست‌ها `none` بود.

## عامل دوم: fallback گستردهٔ FTS و رتبه‌بندی نتایج زیاد

کوئری‌ها در خود اجرای واقعی زمان‌گیری شدند. پس از پایان چهار سرچ، `EXPLAIN (FORMAT JSON)` روی همان SQL و همان پارامترهای ثبت‌شده اجرا شد؛ هیچ مدل یا embedding اضافه‌ای فراخوانی نشد. EXPLAIN بدون ANALYZE است، پس تعداد ردیف‌های طرح تخمین planner است.

|---|---|---:|

مجموع پنج SQL fallback برابر **۳۱٫۶۹ ثانیه، حدود ۲۱٫۷٪ زمان چهار سرچ** بود. محل ساخت آن `backend/apps/ai_retrieval/retrieval.py:159` است. OR کردن تک‌تک مفهوم‌ها می‌تواند رابطهٔ لازم سؤال را ضعیف کند: وجود خود هیپرکالمی یا NSAID همراه زخم در تمام نتایج الزامی نمی‌ماند. سپس `ts_rank_cd` و مرتب‌سازی روی مجموعهٔ بزرگ اجرا می‌شوند؛ `LIMIT 40` فقط خروجی نهایی را محدود می‌کند.

چهار مورد از این پنج OR طرح `Gather Merge → Sort → Seq Scan` داشتند؛ OR اول هیپرکالمی از Bitmap/ایندکس استفاده کرد ولی باز هم ۴٫۷۴ ثانیه طول کشید. بنابراین صرفاً تحمیل استفاده از ایندکس، راه‌حل اثبات‌شده نیست. کوئری‌های strict نمونه از ایندکس FTS استفاده کردند و حدود ۰٫۰۶ تا ۰٫۱۱ ثانیه زمان گرفتند.

## عامل سوم: دو دور جست‌وجو و وابستگی مراحل

هیپرکالمی، تب بدون کانون و NSAID هرکدام دو دور و آریپیپرازول یک دور بازیابی داشتند. سه تماس مدل برای درخواست مکمل، جمعاً **۱۹٫۸۸ ثانیه** اضافه کردند؛ دور دوم بازیابی هم جداگانه به زنجیره افزوده شد. این اعداد هزینهٔ قطعی دور اضافه‌اند، نه اثبات غیرضروری‌بودن آن.

درخواست مکمل هیپرکالمی برای تکمیل جزئیات و پایش، تب برای ارزیابی متناسب با سن/ظاهر و NSAID برای تکمیل پیشگیری/گزینه‌ها انجام شد. برای حذف هر دور باید کفایت پاسخ با شواهد دور اول بررسی شود؛ حذف بدون ارزیابی کیفیت تأیید نشده است.

نوشتن پاسخ نهایی تا پایان این حلقه آغاز نمی‌شود. فقط دو شاخهٔ retrieval موازی‌اند؛ فهم سؤال، دورهای ابزار، تولید متن و تأیید پشت‌سرهم باقی می‌مانند. به همین دلیل concurrency چهار زمان یک سؤال منفرد را تقسیم بر چهار نمی‌کند.

## عامل چهارم: بازبینی پس از اتمام متن

بازبینی چهار سؤال به‌ترتیب **۵٫۹۵، ۳٫۷۰، ۳٫۲۲ و ۳٫۰۸ ثانیه**، جمعاً **۱۵٫۹۵ ثانیه، ۱۰٫۹٪ زمان** گرفت. پاسخ فارسی هیپرکالمی در ثانیهٔ ۴۷ تمام شد و نتیجهٔ بررسی‌شده نزدیک ثانیهٔ ۵۳ آماده شد.

در این چهار اجرا، بازبینی گلوگاه اصلی نبود؛ انتظار API و fallback SQL سهم بیشتری داشتند. کنترل استناد نباید برای بهبود ظاهری زمان حذف شود.

## عامل پنجم: زمینهٔ نسبتاً بزرگ و ارسال دوبارهٔ آن

درخواست فهم سؤال حدود ۲۷۰۸ تا ۲۷۱۳ توکن ورودی داشت؛ بیشتر آن دستورهای ثابت است. ورودی فراخوانی نهایی پاسخ به‌ترتیب **۷۷۳۴، ۵۵۴۹، ۸۹۱۰ و ۸۹۲۶ توکن** بود. شاهدهای دورهای مکمل حفظ و همراه تاریخچهٔ ابزار و دستورها دوباره ارسال می‌شوند، هرچند ابزارهای قدیمیِ superseded از متن شواهد قبلی پاک می‌شوند.

این حجم، بار واقعی پردازش و هزینه را افزایش می‌دهد، اما در این گزارش آزمایش A/B طول prompt انجام نشد؛ سهم علّی آن از انتظار هدر ۲۰٫۸ثانیه‌ای معلوم نیست. سقف ۶۰۰۰ مربوط به بستهٔ شاهد است، نه کل ورودی پیام‌ها و prompt.

## عامل ششم: تعداد زیاد SQLهای کوچک و توسعهٔ پیوندهای منبع

تعداد SQL ثبت‌شده داخل محدودهٔ زمانی هر سؤال: **۳۳۲، ۹۵، ۵۱۷ و ۱۷۹**. SQLهای پاک‌سازی فضای کش پس از اتمام زمان از این شمارش حذف شدند. تعدادها شامل هر دو thread هستند؛ جمع زمان آن‌ها را نباید جای زمان دیواری گذاشت.

بخش توسعهٔ منبع در هیپرکالمی چندین بار بخش، مقاله و پاراگراف را جداگانه می‌خواند؛ در یک الگوی SELECT بخش، ۶۸ بار و در الگوی SELECT مقاله، ۵۵ بار اجرا ثبت شد. در کد `source_context.py`، دنبال‌کردن پیوندها و `section_rows`/`article` از محل‌های این رفت‌وبرگشت‌ها هستند.

زمان دیواری توسعهٔ پیوندها برای چهار سؤال **۱٫۴۹، ۰٫۲۱، ۱٫۹۵ و ۰٫۶۶ ثانیه** بود. این هزینه وجود دارد، اما در محیط محلی فعلی از SQL گسترده و انتظار API کوچک‌تر بود. اثر آن زیر بار یا با دیتابیس دور از worker اندازه‌گیری نشد. batching/prefetch و حذف خواندن‌های تکراری، موضوع اصلاح جداگانه‌اند؛ قطع کورکورانهٔ پیوندهای منبع ممکن است شاهد لازم را حذف کند.

## عوامل موجود در مسیر استریم سرور که در این اجرای مستقیم سنجیده نشدند

کد واقعی job کار بیشتری از callback سبک این آزمایش انجام می‌دهد:

1. در `streaming.py:84` به‌ازای هر SSE، `check_cancelled` فراخوانی می‌شود؛ پیاده‌سازی واقعی آن در `views.py:83` یک GET همگام cache دارد. این کنترل در جریان بازبینی نیز انجام می‌شود.
2. در `views.py:198` به‌ازای هر قطعهٔ پاسخ، لغو دوباره بررسی، job خوانده، پیش‌نویس کامل به record افزوده و کل record در cache نوشته می‌شود؛ سپس `events.append` فرمان Redis دیگری می‌فرستد.
3. `jobs.read` در `jobs.py:44` برای job فعال hybrid حتی با cache hit، وضعیت SQL را می‌خواند. پس انتشار هر delta می‌تواند یک SELECT دیتابیس اصلی نیز داشته باشد.
4. record شامل یافته‌ها و نقل‌قول‌هاست؛ بازنویسی آن با هر قطعه، علاوه بر رفت‌وبرگشت، serialization مکرر ایجاد می‌کند. این کارها داخل callback همگام انجام می‌شوند و می‌توانند خواندن قطعهٔ بعدی upstream را عقب بیندازند.
5. ثبت مصرف هر فراخوانی و تسویهٔ نهایی نیز در مسیر durable انجام می‌شوند؛ اجرای مستقیم این آزمایش reservation اعتباری نداشت. صف Celery، ظرفیت و رقابت منابع، بخش‌های دیگری از مسیر واقعی‌اند.

این موارد از کد تأیید می‌شوند، اما برایشان عددی از رانفلر ادعا نشده است. batch کردن انتشار در بازهٔ کوتاه، کاهش نرخ polling لغو و جلوگیری از SELECT وضعیت SQL روی هر delta، گزینه‌های بررسی‌اند؛ باید لغو، بازیابی و نتیجهٔ پایدار حفظ شوند.

## عوامل کوچک‌تر یا مواردی که توضیح اصلی این اجرا نبودند

- اتصال PostgreSQL: مجموع زمان اتصال‌های تازهٔ هر سؤال حدود **۰٫۰۳ تا ۰٫۰۶ ثانیه**؛ عامل انتظار ده‌ها ثانیه نبود.
- query برداری: جمع هر سؤال **۱٫۰۰، ۰٫۲۳، ۰٫۳۶ و ۰٫۹۶ ثانیه**؛ ساخت مجدد corpus یا embedding اسناد انجام نشد.
- embedding پرسش: جمع هر سؤال **۴٫۰۲، ۱٫۸۲، ۳٫۱۳ و ۳٫۵۵ ثانیه**؛ با FTS موازی بود. در سه سؤال دو embedding لازم شد. embedding شکست نخورد و semantic fallback ثبت نشد.
- نگهداری امنیتی ۱۲۸ کاراکتر انتهایی در آداپتور: تأخیر اولین callback نسبت به متن خام حدود **۰٫۲۰۸، ۰٫۰۰۳، ۰٫۰۳۷ و ۰٫۰۰۴ ثانیه**؛ علت انتظار ۲۹ تا ۴۶ثانیه‌ای اولین متن نبود.
- بازبینی بالینی/کیفیت: partial تب بدون کانون وارد کش پاسخ نهایی نمی‌شود. سه answered واجد شرایط بررسی ذخیرهٔ کش هستند. نرخ hit واقعی کاربران و warm-run در این نوبت اندازه‌گیری نشد؛ سؤال یا تاریخچهٔ متفاوت و حساب متفاوت نیز کلید کش متفاوت دارند.
- کد فعلی سقف زمانی سراسریِ پاسخ کامل ۲۰ثانیه‌ای ندارد. timeout شبکهٔ هر فراخوانی، جای deadline کل سرچ را نمی‌گیرد؛ این نبود سقف، علت SQL کند نیست، اما اجازه می‌دهد تأخیر مراحل جمع شود.
- رابط فعلی skeleton و عبارت‌های عمومی را تا پایان نگه می‌دارد. مرحله‌های planning/retrieving/verifying رویداد مستقلِ مصرف‌شونده در رابط ندارند. این مسئله حس توقف ایجاد می‌کند و CPU مدل را کند نمی‌کند.

## ترتیب اقدام

۱. fallback FTS را با حفظ موجودیت/رابطهٔ سؤال و محدودکردن مجموعهٔ واقعی رتبه‌بندی بازطراحی و با کیفیت منابع ارزیابی کنید. کندی OR در خود چهار اجرای اصلی و طرح SQL دقیق تأیید شد.

۲. کفایت دور اول و علت دور دوم را بررسی کنید؛ سه دور مکمل حدود ۱۹٫۹ ثانیه تماس مدل اضافه داشتند. متن prompt و metadata تکراری فقط با آزمون حفظ استناد و کیفیت کوتاه شوند.

۳. نگهداشت اتصال و I/O مسیر انتشار را اصلاح و اعتبارسنجی کنید؛ تعداد خواندن‌های وضعیت و منبع کاهش یابد و انتشار batch شود. سپس با job واقعی و استریم، هزینهٔ اضافهٔ durable اندازه‌گیری شود. مکانیزم بسته‌شدن اتصال در [آزمایش ۴۰ درخواست](provider-latency-40-requests-2026-11-18.fa.md) بررسی شده است؛ مقدار بهبود زنده هنوز معلوم نیست.

۴. انتظار API و زمان کل اپ را از هم جدا نگه دارید. آزمایش ۴۰ درخواست انجام شده، اما علت داخلی انتظار ارائه‌دهنده و سهم صف/انتشار/نمایش در سرور را تعیین نمی‌کند. ارزیابی اصلاحات با همان مدل و تنظیم‌های ثابت انجام شود.

۵. وضعیت واقعی پیش از متن و پس از پایان تولید را در اپ نشان دهید. فعال‌کردن draft به‌تنهایی نمی‌تواند اولین متن هیپرکالمی را از ثانیهٔ ۴۶ به ابتدای کار منتقل کند.

چهار اجرا برای ادعای «تمام علل سرور» یا p95 کافی نیستند. با این حال، انتظار API، fallbackهای SQL، دورهای مکمل، تأیید پس از متن و حجم رفت‌وبرگشت‌های منبع با زمان مشخص ثبت شدند؛ بقیهٔ هزینه‌های مسیر سرور صریحاً از آن‌ها جدا شده‌اند. منطق اپ، تنظیمات فعال، ایندکس و مدل تغییر نکردند؛ فقط گزارش و دادهٔ تشخیصی اضافه شدند.
