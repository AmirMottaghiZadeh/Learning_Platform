# گزارش فاز ۱: ارزیابی اولیهٔ UpToDate

> **سند تاریخی؛ طرح لغوشده در ۲۰۲۶/۱۱/۱۰.** کد موتور آزمایشی، واژه‌نامه‌ها و ابزارهای ارزیابی این گزارش حذف شده‌اند. دستورهای این سند را اجرا نکنید و برنامهٔ آن را ادامه ندهید. وضعیت نهایی در [گزارش حذف](../../24-offline-smart-search-removal.fa.md) است؛ جست‌وجوی فعال اپ تغییر نکرده است.

> **سند تاریخی:** این گزارش مربوط به پایلوت کنارگذاشته‌شدهٔ ۲۰۲۶-۱۰-۲۷ تا ۳۰ است. وضعیت‌ها و دستورهای آن شرح همان زمان‌اند. فایل‌های حذف‌شده با مسیر آرشیوی، بدون پیوند اجرایی، آمده‌اند؛ محل آرشیو و برنامهٔ جایگزین در [راهنمای سابقه](README.md) است.

تاریخ: ۲۰۲۶-۱۰-۲۸. نتیجه: بررسی فقط‌خواندنی ساختار داده و تهیهٔ چارچوب ارزیابی انجام شد. **کیفیت بالینی جست‌وجو، تعداد واقعی chunk، مدل، ظرفیت کامل و کیفیت ارجاع هنوز اندازه‌گیری یا تأیید نشده‌اند.**

## کار انجام‌شده و روش

- مسیر موجود `UPTODATE_DB_DIR` و پیاده‌سازی SQLite، MySQL، جست‌وجو، نمایش مقاله و حالت آفلاین بررسی شد. فایل‌ها تغییر نکردند و اتصال MySQL یا تولید استفاده نشد.
- اسکریپت فقط‌خواندنی audit_uptodate.py (`audit_uptodate.py`؛ مسیر آرشیوی) `fts.db` و `content.db` را مستقیم از SQLite باز می‌کند، شناسه‌های متمایز `type=1` را مرتب و با seed ثابت نمونه‌گیری می‌کند، JSON فشرده را باز می‌کند و شمارش تجمعی HTML را بدون ذخیره متن یا شناسه مقاله گزارش می‌کند.
- دستور: `python3 docs/search/audit_uptodate.py --source /home/amir/Documents/UpToDate --sample 500 --seed 20261028`؛ نتیجهٔ ماشین‌خوان JSON (`uptodate-audit-2026-10-28.json`؛ مسیر آرشیوی) است. نمونه تصادفی ساده است، نه نمونهٔ طبقه‌بندی‌شده بر اساس تخصص یا طول مقاله.
- ۳۴ پرسش اولیه در evaluation-queries.csv (`evaluation-queries.csv`؛ مسیر آرشیوی) آماده شد؛ پرسش‌ها برچسب ارتباط یا پاسخ بالینی تأییدشده ندارند و صرفاً نقطهٔ شروع داوری‌اند.

## مشاهدات داده

| شاخص | نتیجه |
|---|---:|
| کل ردیف‌های FTS، شامل انواع دیگر | ۶۲٬۱۲۶ |
| شناسهٔ یکتای مقاله در FTS با `type=1` | ۲۲٬۲۱۷ |
| کل ردیف‌های content، شامل انواع دیگر | ۶۲٬۲۲۸ |
| مقالات نمونهٔ انتخاب‌شده و خوانده‌شده | ۵۰۰ از ۵۰۰ |
| HTML بدنهٔ خالی در نمونه | ۰ |
| مقاله دارای یک یا چند `id` در HTML | ۵۰۰ |
| مقاله دارای `id` تکراری در همان بدنه | ۶۴ |
| تگ‌های `p` و `li` | ۹۳٬۷۸۷؛ از این تعداد ۶٬۴۶۷ دارای `id` |
| مقاله دارای `table` | ۳۹ |
| مقاله دارای تگ `p`/`li` تو‌در‌تو | ۲؛ در مجموع ۱۲ تگ تو‌در‌تو |
| مقاله دارای نویسهٔ محدودهٔ عربی/فارسی در متن HTML نمونه | ۰ |

میانگین تعداد تگ `p`/`li` در مقاله ۱۸۷٫۵۷، میانه ۱۴۰، صدک ۹۰ برابر ۳۹۷ و بیشینه ۱٬۰۶۲ است. میانگین حجم HTML حدود ۶۲٬۱۶۹ بایت و میانه حدود ۴۸٬۸۳۹ بایت است. حاصل‌ضرب خام میانگین نمونه در کل شناسه‌ها حدود ۴٫۱۷ میلیون تگ می‌شود؛ **این رقم تعداد chunk یا برآورد نهایی بردار نیست**: منابع کتاب‌شناختی و ساختارهای تکراری در تگ‌ها هستند، موارد تو‌در‌تو ممکن است هم‌پوشانی داشته باشند و پاراگراف بلند نیز ممکن است تقسیم شود. مشاهدهٔ صفر نویسهٔ فارسی تنها به این نمونه مربوط است.

اندازهٔ فایل‌ها بر اساس `du -h`: `content.db` حدود ۳۷۸ MiB، `fts.db` حدود ۹۳۶ MiB، `toc.db` حدود ۲۵ MiB و `images.db` حدود ۶۴۶ MiB؛ فضای مصرفی دیسک است نه اندازهٔ index آینده. `info.json` فعلی مقدار `version: 1` دارد؛ این عدد به‌تنهایی نباید به عنوان نسخهٔ محتوای هر مقاله یا اثر انگشت snapshot فرض شود. هر ردیف `content` نیز فیلد `version` دارد؛ لازم است در فاز بعد پایداری و معنی آن همراه hash بدنه آزمایش شود.

## آثار بر طراحی

1. چون `id`های تکراری و پاراگراف‌های بدون `id` وجود دارند، `document.getElementById` به‌تنهایی مکان دقیق همهٔ نتایج را تضمین نمی‌کند. از headingهای موجود برای ارجاع تقریبی استفاده شود و برای بلوک‌ها نگاشت نسخه‌دار ساخته و در HTML رندرشده با دادهٔ واقعی آزمایش شود. parser سمت سرور و DOM مرورگر، تگ‌های ناقص یا تو‌در‌تو را ممکن است متفاوت تفسیر کنند؛ همسانی مسیرها باید در وب و WebView تأیید شود.
2. ساختار `outlineHtml` به شناسه‌های بخش در `bodyHtml` وصل است و صفحهٔ فعلی قابلیت رفتن به بخش دارد. این قابلیت نقطهٔ شروع fallback است، نه اثبات ارجاع به همهٔ پاراگراف‌ها.
3. مسیر `uptodateSource` ابتدا بستهٔ آفلاین را می‌خواند. نتیجهٔ آنلاین ممکن است به نسخهٔ دیگری از مقاله اشاره کند؛ بررسی نسخه و انتخاب نسخهٔ سازگار قبل از اسکرول ضروری است.
4. جست‌وجوی موجود عنوان‌محور است؛ snippet فعلی عملاً خالی است. نمایش متن مقاله در نتایج هوشمند سیاست مجوز/سهمیه جداگانه می‌خواهد. انتقال کامل SQLite به PostgreSQL برای آزمایش این معماری لازم نیست.
5. تصاویر/جداول به ارزیابی جداگانه نیاز دارند. نمونهٔ ۵۰۰تایی همهٔ اشکال محتوا و تصاویر ارجاع‌شده را پوشش نمی‌دهد؛ نحوهٔ تبدیل جدول و حذف ارجاعات کتاب‌شناختی هنوز تصمیم نهایی نیست.

## برنامهٔ ارزیابی کیفیت

فایل پرسش‌ها شامل زبان، دسته، query و وضعیت `unjudged` است. برای تبدیل آن به benchmark معتبر، ۱۰۰ تا ۲۰۰ پرسش متنوع واقعی به آن اضافه و برای هر پرسش، مقاله و محل مرتبط با نسخهٔ محتوا ثبت شود. داور آشنا به محتوای دارویی باید درجهٔ ارتباط هر نتیجه را تعیین کند؛ بهتر است نمونه‌ای مستقل دو بار داوری و اختلاف‌ها حل شود. پرسش‌های فارسی/انگلیسی مشابه می‌توانند برای سنجش بین‌زبانی جفت شوند. پرسش دارای عدد، واحد، نفی، نام تجاری و غلط تایپی باید پوشش داده شود.

روی corpus و snapshot یکسان، جست‌وجوی عنوان فعلی، BM25، برداری و ترکیبی را با همان دادهٔ داوری‌شده مقایسه کنید: Recall@10 و nDCG@10 در سطح مقاله و در صورت وجود برچسب، سطح پاراگراف؛ همچنین p50/p95، زمان ساخت و حافظه. هیچ عدد کیفیتی پیش از اجرای آزمایش و داوری وجود ندارد.

## تست‌ها و محدودیت‌ها

اسکریپت در برابر snapshot واقعی به پایان رسید و خروجی JSON آن ذخیره شد. مشاهدهٔ حجم فایل‌ها و شمارش SQLite مستقل از اسکریپت انجام شد. در این فاز اتصال Elasticsearch، ساخت مدل، مقایسهٔ ranking، اجرای Django یا تغییر API انجام نشده است. منابع/نسخهٔ Elasticsearch و مجوزهای آن، مجوز پردازش متن در سرویس embedding، منابع embedding و بودجه، و تعریف دقیق دسترسی به snippet هنوز باید تعیین شوند.

## ادامهٔ پیشنهادی

فاز ۲: یک استخراج‌کنندهٔ نمونه و قابل تکرار روی زیرمجموعهٔ متنوع بسازید؛ تطبیق DOM و anchor را در وب و WebView، تغییر نسخه و fallback تست کنید؛ سپس تعداد واقعی بلوک‌ها و chunkها را با tokenizer مدل‌های نامزد اندازه بگیرید. هم‌زمان داوری مجموعهٔ پرسش‌ها را شروع کنید. بعد از هر فاز مطابق [قرارداد نگهداری](README.md) گزارش جدید ثبت شود.
