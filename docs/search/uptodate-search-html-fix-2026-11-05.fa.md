# گزارش اصلاح جست‌وجو، تخصص‌ها و نمایش HTML در UpToDate

تاریخ: ۲۰۲۶-۱۱-۰۵

اصلاحات در کد محلی بک‌اند، اپ و سازندهٔ بستهٔ آفلاین اعمال و بررسی شدند. دیتابیس‌های منبع در `/home/amir/Documents/UpToDate` فقط با اتصال خواندنی بررسی شدند و تغییر نکردند. انتشار روی سرور یا ساخت و انتشار نسخهٔ موبایل در این مرحله انجام نشده است.

## علت مشکل جست‌وجو و تگ‌ها

دیتابیس منبع ساختار لازم را از قبل دارد. جدول `query` در `search.db` شامل ۱۵۷٬۱۶۴ عبارت و نام جایگزین برای ۸۵٬۵۸۸ مفهوم متمایز است. جدول `query_topic` شامل ۱۱۶٬۵۹۲ ردیف ارتباط با مقاله و فهرست‌های مرتب‌شدهٔ `x_topic_hits`، `a_topic_hits`، `p_topic_hits` و `i_topic_hits` است. فهرست‌های عمومی، بزرگسال، کودکان و آموزش بیمار اکنون در انتخاب نتایج استفاده می‌شوند.

جست‌وجوی قبلی عمدتاً کلمات عنوان را تطبیق می‌داد و این ارتباط‌ها را نمی‌خواند. بنابراین عبارت کوتاه یا نام جایگزین، نتایج مطلوب و ترتیب موجود در منبع را بازتولید نمی‌کرد. تطبیق پیشوندی `h` و `pylori` حتی می‌توانست مقالهٔ نامرتبط `Hypertrophic pyloric stenosis in infants` با شناسهٔ `5890` را برگرداند.

مشکل تخصص‌ها مستقل از این موضوع بود: هر مقاله می‌تواند در چند شاخهٔ `toc.db` باشد، ولی کد قبلی تنها اولین شاخه را نگه می‌داشت. مقالهٔ درمان با شناسهٔ `140619` در چهار تخصص، از جمله گوارش، حضور دارد؛ کنارگذاشتن مسیرهای دیگر آن را از بعضی فیلترهای درست حذف می‌کرد. رابط کاربری نیز تنها چهار فیلتر تخصص را نشان می‌داد. این فیلترها «تخصص» هستند؛ پیشنهادهای عبارت جست‌وجو اکنون در ردیف جداگانه‌ای نمایش داده می‌شوند.

## تغییرات اعمال‌شده

- اتصال نام‌ها و عبارت‌های جایگزین به مفهوم و سپس مقاله‌های مرتبط، با حفظ ترتیب فهرست منبع؛ اولویت با تطبیق کامل عبارت و سپس طولانی‌ترین عبارت شناخته‌شده در پرس‌وجو است.
- باقی‌ماندن جست‌وجوی عنوان و تصحیح غلط تایپی برای عبارت‌های ناشناخته. برای مفهوم شناخته‌شده، تکمیل نتایج با تطبیق کامل کلمات عنوان انجام می‌شود تا پیشوندهای کوتاه نتیجهٔ نامرتبط اضافه نکنند.
- اعمال کلمات اضافی کاربر بر عنوان نتایج؛ برای مثال افزودن `refractory` صرفاً نادیده گرفته نمی‌شود.
- پیشنهاد عبارت‌های مرتبط از همان کاتالوگ منبع، بدون تکرار مفهوم و بدون پیشنهاد مفهومی که مقالهٔ موجود ندارد.
- نگهداری تمام تخصص‌های هر مقاله در API، موتور آفلاین و بسته‌های جدید؛ فیلتر تخصص هر یک از این عضویت‌ها را می‌پذیرد. شمارش در هر تخصص بدون تکرار مقاله است؛ چون یک مقاله چند تخصص دارد، جمع تعداد تخصص‌ها می‌تواند از تعداد کل نتایج بیشتر باشد.
- نمایش تمام فیلترهای تخصص در ردیف قابل پیمایش، همراه با پیشنهادهای قابل انتخاب و بهبود دسترس‌پذیری کنترل‌ها در رابط فارسی و انگلیسی.
- اجرای یک منطق همسان در Python و TypeScript برای ترتیب، پیشنهادها، فیلتر، شمارش و صفحه‌بندی.

در بررسی snapshot کامل، `h pylori` تعداد ۴۲ نتیجه داشت و مقالهٔ `140619` اولین نتیجه بود. با فیلتر `Gastroenterology and Hepatology` تعداد ۳۴ نتیجه داشت و همان مقاله همچنان اول بود. مقالهٔ نامرتبط `5890` در نتایج این پرس‌وجو نبود. این شمارش مربوط به دادهٔ فعلی است و با تغییر snapshot می‌تواند تغییر کند.

## علت و اصلاح HTML در عنوان و متن

در ۲۲٬۲۱۷ عنوان قابل جست‌وجو، ۱۷۶ عنوان دارای تگ HTML و ۹ عنوان دارای entity یافت شد؛ این دو گروه الزاماً جدا نیستند. قالب‌هایی مانند `<i>…</i>` بخشی از دادهٔ واردشده بودند، ولی خروجی بعضی مسیرها مستقیماً داخل کنترل متنی نمایش داده می‌شد. پاک‌کننده‌های قبلی نیز یکسان نبودند و HTML دوباره escape‌شده را کامل پوشش نمی‌دادند.

عنوان‌ها اکنون در مرز API و ساخت بسته به متن ساده تبدیل می‌شوند. کلاینت نیز عنوان بسته‌های قدیمی، نتایج، مسیر مقاله، outline، عنوان گرافیک و عنوان‌های علاقه‌مندی این صفحه را پاک می‌کند. entity پیش از حذف تگ decode می‌شود و لایه‌های متداول escape پوشش داده می‌شوند. علامت‌های بالینی مانند `<7`، `>5`، `≥` و `≤` حفظ می‌شوند؛ entity عددی نامعتبر هم باعث خطای کلاینت نمی‌شود.

در متن مقاله، پس از کنارگذاشتن کدهای `script` و `style`، سه مورد واقعی از تگ قالب‌بندی escape‌شده در ارجاعات شناسایی شد:

| شناسه | مقاله | نمونهٔ دادهٔ معیوب |
|---|---|---|
| `6695` | Chemical pleurodesis | `&lt;em&gt;versus&lt;/em&gt;` |
| `4621` | ALK-positive lung cancer | `&lt;I&gt;ALK&lt;/I&gt;` |
| `4728` | Richter transformation | `&lt;I&gt;de novo&lt;/I&gt;` |

این تگ‌ها هنگام parse اولیه به نوشتهٔ قابل مشاهده تبدیل می‌شدند. خوانشگر اکنون پس از parse، فقط تگ‌های سادهٔ قالب‌بندی `i/em/b/strong/sub/sup` را در گره‌های متنی به عنصر DOM کنترل‌شده تبدیل می‌کند. این تبدیل attribute یا HTML دلخواه را اجرا نمی‌کند و از بخش‌های کد و اسکریپت عبور می‌کند. جدول، لینک، علامت‌های مقایسه و قالب‌بندی عادی مقاله حفظ می‌شوند.

HTML خام مقاله در API و دیتابیس بازنویسی نشده است؛ بنابراین هش متن و سازوکار anchor جست‌وجو ثابت می‌مانند. اصلاح نمایش روی مقالهٔ آنلاین، محتوای cache و بستهٔ قدیمی هم اعمال می‌شود.

## سازگاری بسته‌های آفلاین قبلی

بسته‌های جدید با `search_schema: 1` کاتالوگ جست‌وجو و تمام تخصص‌ها را در index دارند. برای بستهٔ قدیمی، اپ جدید در پس‌زمینه مکمل رمزگذاری‌شدهٔ `search-v1.bin` را از مسیر زیر دریافت می‌کند:

`GET /api/v1/uptodate/search-metadata/?build=...&version=...`

مکمل فقط متادیتای جست‌وجو و تخصص‌ها دارد و با کلید موجود همان build رمزگذاری می‌شود. اندازهٔ فشردهٔ آن در snapshot بررسی‌شده ۱۵٬۵۹۰٬۶۴۴ بایت، حدود ۱۵٫۶ مگابایت است. نیازی به دانلود دوبارهٔ متن‌ها و تصاویر نیست. دریافت آن به دسترسی معتبر پولی آفلاین، تنظیم کلیدهای آفلاین سرور و تطابق نسخهٔ snapshot نیاز دارد.

پس از دریافت، index آماده‌شده و نتایج جست‌وجوی حافظه تازه می‌شوند. علاقه‌مندی‌ها، هایلایت‌ها و فایل‌های اصلی بسته باقی می‌مانند. قطع اینترنت یا خرابی مکمل، جست‌وجوی قبلی را از کار نمی‌اندازد؛ درخواست ناموفق حداکثر پس از یک دقیقه دوباره قابل تلاش است. بسته با snapshot متفاوت مکمل نسخهٔ دیگری را نمی‌پذیرد.

## نتیجهٔ اعتبارسنجی

| بررسی | نتیجه |
|---|---|
| تست‌های Django برای `apps.uptodate` و `apps.offline` روی PostgreSQL موقت و مستقل | ۱۷۳ تست موفق |
| تطابق موتور آنلاین و آفلاین با snapshot کامل | ۲۸ سناریوی موفق، شامل نام جایگزین، عبارت تکمیلی، تخصص و صفحه‌بندی |
| بررسی عنوان‌های snapshot | تمام ۲۲٬۲۱۷ عنوان بدون تگ HTML پس از تبدیل |
| تست‌های TypeScript از طریق اسکریپت Node | موفق؛ شامل بستهٔ قدیمی، دریافت/ذخیره/خرابی مکمل و HTML |
| تست ناوبری جست‌وجو و تبدیل DOM متن مقاله | موفق |
| `npm run typecheck` | موفق |
| `npm run build:web` | موفق |
| Chrome واقعی، خوانشگر و سه مقالهٔ دارای ارجاع معیوب | موفق؛ حفظ جدول، لینک، مقایسه‌ها و جست‌وجوی داخل مقاله |
| رابط جست‌وجوی فارسی و انگلیسی در عرض‌های ۳۹۰، ۷۶۸ و ۱۴۴۰ پیکسل | موفق؛ انتخاب فیلتر و پیشنهاد و ترتیب نتایج بررسی شد |

بررسی رابط با API شبیه‌سازی‌شده و نتایج استخراج‌شده از snapshot انجام شد؛ تست API بک‌اند جداگانه اجرا شد. بررسی MySQL با mock جدول‌های آینه انجام شد و اتصال زنده به MySQL تولید انجام نشد. تست مرورگر جایگزین تست روی دستگاه واقعی Android یا iOS نیست؛ این مرحله روی دستگاه واقعی اجرا نشده است.

فایل‌های تست و گزارش‌های تصویری موقت در `/tmp/lp-search-browser` و fixture تطابق در `/tmp/lp-search-parity.json` قرار دارند. این داده‌های تولیدی وارد مخزن نشده‌اند.

## فایل‌های اصلی و انتشار

منطق سرور در [services.py](../../backend/apps/uptodate/services.py)، کاتالوگ در [search_catalog.py](../../backend/apps/uptodate/search_catalog.py)، پاک‌سازی عنوان در [text.py](../../backend/apps/uptodate/text.py) و ساخت بسته در [builders.py](../../backend/apps/offline/builders.py) قرار دارد. منطق آفلاین در [uptodateLocal.ts](../../frontend/src/offline/uptodateLocal.ts) و [uptodateSearchCatalog.ts](../../frontend/src/offline/uptodateSearchCatalog.ts)، مکمل در [uptodateSearchSupplement.ts](../../frontend/src/offline/uptodateSearchSupplement.ts) و اصلاح متن در [UptodateArticleScreen.tsx](../../frontend/src/screens/UptodateArticleScreen.tsx) است.

برای در دسترس قرارگرفتن این رفتار برای کاربران، کد بک‌اند و نسخهٔ جدید وب/موبایل باید منتشر شوند. migration پایگاه دادهٔ اصلی لازم نیست. ساخت بستهٔ تازه توصیه می‌شود تا متادیتا از ابتدا داخل آن باشد؛ کاربران بسته‌های قبلیِ هم‌نسخه، پس از به‌روزرسانی اپ و یک اتصال موفق، مکمل را دریافت می‌کنند. API قدیمی و ساختار اصلی بسته برای سازگاری حفظ شده‌اند.
