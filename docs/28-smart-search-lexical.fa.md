# فاز دو سرچ هوشمند: رتبه‌بندی منظور سؤال و بازیابی واژگانی

ادامهٔ پیاده‌سازی در [فاز سه، انتخاب محلی شواهد](29-smart-search-local-selection.fa.md) انجام شده است. انتخاب بخش توسط مدل و چهار فراخوانیِ متداولِ این سند، مربوط به مسیر فاز دو و حالت برگشت‌اند؛ پیش‌فرض تازه بخش‌ها را محلی انتخاب می‌کند.

تاریخ: ۲۰۲۶/۱۱/۱۱. این فاز از دادهٔ آمادهٔ [فاز یک](27-smart-search-preprocessing.fa.md) استفاده می‌کند تا مقاله‌های نامزد، بخش‌ها و بندهای مرتبط پیش از ارسال به مدل مرتب شوند. بردارسازی اضافه نشده است. سرچ معمول اپ، tagging، فایل‌های منبع و بازکردن ارجاع در اپ تغییر نمی‌کنند.

## جریان اجرا

1. همان فراخوانی برنامه‌ریزی، علاوه بر عبارت کوتاه کاتالوگ، `intent` و حداکثر هشت عبارت انگلیسی برای جنبهٔ صریح سؤال می‌دهد. این عبارت‌ها قرار نیست جواب، داروی پیشنهادی یا تشخیص حدسی باشند. عبارت کاتالوگ همچنان کوتاه می‌ماند.
2. همان `uptodate.services.search_page` نامزدها را با مفهوم‌ها، aliasها و tagging موجود می‌دهد. فقط در مسیر سرچ هوشمند، `lexical.rank_topics` آن‌ها را بر اساس نوع منبع، مخاطب و جنبهٔ سؤال دوباره مرتب می‌کند. در سؤال کلی درمان، overview مدیریت بر مقالهٔ مخصوص یک زیرگروه اولویت می‌گیرد؛ با درخواست صریح درمان موضعی، شدت مشخص، نارسایی کلیوی یا وضعیت خاص این امتیاز عمومی اعمال نمی‌شود. هیچ نامزدِ صرفاً tagged حذف و هیچ شناسه‌ای اختراع نمی‌شود؛ تساوی رتبه، ترتیب اصلی را حفظ می‌کند. صفحهٔ فعلی همچنان ۳۰ نتیجه دارد.
3. مقاله‌ها یکی‌یکی خوانده می‌شوند. فهرست فرمولاسیون دارو همچنان فقط لینک‌های دارویی صریحِ منبع را قبل از سایر مقاله‌ها دنبال می‌کند. دسترسی و سهمیه پیش از خواندن متن بررسی می‌شوند.
4. پس از تطبیق تازگی نسخهٔ آماده، PostgreSQL در **همان مقاله** با `to_tsvector('english', ...)` و `SearchQuery` واژه‌ها را جست‌وجو و با `SearchRank` مرتب می‌کند. ریشه‌یابی انگلیسی فعال است؛ شرط پرس‌وجو پارامتری است و SQL یا عملگر دلخواه مدل اجرا نمی‌شود.
5. عنوان خود بخش، مسیر عنوان‌های والد، جنبهٔ مورد سؤال و امتیاز بهترین بند، ترتیب بخش‌ها را تعیین می‌کنند. بخش‌های بعد از شمارهٔ ۶۰ نیز در این مرحله قابل انتخاب‌اند. حداکثر ۱۶ بخش به انتخاب‌گر مدل می‌رسد.
6. حداکثر ۹۶ تطبیق واژگانی به‌علاوهٔ دو بند آغازین بخش‌های منتخب، مخزن محدود شواهد را می‌سازند. بند آغازین برای حفظ زمینه و قیدها باقی می‌ماند، حتی اگر واژهٔ جست‌وجو در آن نباشد. بندهای هر بخش بر اساس ارتباط مرتب می‌شوند؛ پوشش واژه‌های جنبهٔ سؤال و برای درمان کلی، عبارت توصیهٔ صریحِ خود منبع، بر تکرار زیاد واژهٔ بیماری وزن بیشتری می‌گیرند.
7. مدل هنوز بخش‌ها را انتخاب می‌کند. سپس حداکثر ۱۸ بند کامل و در مجموع حداکثر ۲۴٬۰۰۰ نویسه انتخاب می‌شوند؛ ابتدا به هر بخش منتخب فرصت داده می‌شود. متن بند برای جا شدن بریده یا بازنویسی نمی‌شود. پاسخ و بررسی کفایت همچنان در دسته‌های شش‌بندی انجام می‌شوند. تأیید پاسخ کافی، ادامهٔ خواندن همان مقاله و تمام مقاله‌های بعدی را متوقف می‌کند.

برای مثال در سؤال تأیید ریشه‌کنی پس از درمان، عبارت‌های مشخصی مثل confirmation / eradication / test of cure می‌توانند از کاربرد فرعی واژهٔ treatment مهم‌تر باشند. این وزن‌ها برای یافتن منبع‌اند و به‌تنهایی پاسخ پزشکی تولید نمی‌کنند.

## ایندکس، سازگاری و برگشت

کد اصلی در [lexical.py](../backend/apps/ai_lab/lexical.py) است. migration `ai_lab.0002_reference_paragraph_fts` ایندکس GIN با نام `ref_paragraph_fts_idx` را روی متن بندهای دارای شمارهٔ بازیابی می‌سازد. این SearchVector واژگانی است، embedding یا pgvector نیست. دادهٔ مشتق‌شده و نسخهٔ کامل موجود دوباره از منبع استخراج نمی‌شوند؛ نسل‌های آینده نیز خودکار در همین ایندکس قرار می‌گیرند.

ساخت ایندکس PostgreSQL با `CREATE INDEX CONCURRENTLY` و migration غیراتمیک انجام می‌شود تا نوشتن جدول در تمام زمان ساخت مسدود نشود. اگر ساخت قطع شود و ایندکس invalid باقی بماند، اجرای مجدد migration آن را تعمیر می‌کند. ساخت روی منبع پرحجم می‌تواند چند دقیقه طول بکشد؛ در انتشار با سقف زمان startup کوتاه، migration را پیش از rollout در job یا ترمینال بک‌اند اجرا کنید و برای پایانش زمان کافی بدهید. SQLite اصلی منبع تغییر نمی‌کند. در backend آزمایشی غیر PostgreSQL، ساخت GIN رد می‌شود و مسیر درون حافظه برای آزمون کار می‌کند.

```dotenv
AI_LAB_LEXICAL_ENABLED=True
AI_LAB_PREPROCESSED_MODE=prefer
```

با `AI_LAB_LEXICAL_ENABLED=False`، خواندن و بودجهٔ قبلیِ حداکثر ۶۰ بخش و ۴۸ بند برمی‌گردد. ساختار خروجی برنامه‌ریزی همچنان می‌تواند intent و keywords را داشته باشد. بعد از تغییر تنظیم، workerهای بک‌اند را restart کنید.

حالت‌های off/prefer/require پیش‌پردازش مستقل‌اند. در prefer، نبود نسخهٔ آماده یا خطای دیتابیس باعث استخراج قبلی و رتبه‌بندی واژگانی در حافظه می‌شود؛ سلسله‌مراتب فقط وقتی از دادهٔ آمادهٔ معتبر در دسترس باشد در رتبه‌بندی شرکت می‌کند. در require، دادهٔ کهنه یا ناموجود پذیرفته نمی‌شود. fallback درون حافظه ریشه‌یابی کامل PostgreSQL ندارد و تضمین رتبهٔ کاملاً یکسان نمی‌دهد.

همان `content_hash`، `sectionId` و `searchAnchor` اصلی به نتیجه می‌رسند؛ متن‌ها و شناسه‌های P شماره‌گذاریِ اصلی را حفظ می‌کنند. کنارگذاری جدول پیچیده و متن خارج از بازهٔ ۴۰ تا ۶۰۰۰ نویسه حفظ شده است. محدودشدن نامزدها و بودجه در `limited` ثبت می‌شود؛ `not_found` همچنان به معنی جست‌وجوی کامل تمام دیتابیس نیست.

## استقرار

پس از انتشار کد، از مسیر backend:

```bash
python manage.py migrate ai_lab --noinput
python manage.py build_reference_index --status
```

اگر نسخهٔ کامل و سازگار فاز یک از قبل ساخته نشده است:

```bash
python manage.py build_reference_index --workers 2 --batch-size 20
```

ایندکس متن با migration ایجاد می‌شود؛ فرمان جداگانهٔ ساخت vector وجود ندارد. ساخت لوکال، ایندکس سرور را ایجاد نمی‌کند. متغیرهای مدل، base URL، reasoning و کلید API در این فاز تغییری نمی‌کنند. رابط اپ به build تازه نیاز ندارد؛ قرارداد عنوان‌ها، بخش‌ها و یافته‌های تدریجی حفظ شده است.

## بررسی آفلاین بدون مصرف API

```bash
python manage.py evaluate_lexical_retrieval \
  --repeat 3 \
  --output exports/phase2-lexical-retrieval.json
```

[lexical_cases.json](../backend/apps/ai_lab/benchmark/lexical_cases.json) بیست برنامهٔ انگلیسیِ تألیفی از سؤال‌ها دارد. فرمان ابتدا ترتیب نامزدهای سرچ معمول را جداگانه می‌سنجد؛ سپس **مقالهٔ موردانتظار** مجموعهٔ فاز صفر را برای آزمون مستقلِ درون مقاله می‌خواند. عنوان‌های موردانتظار فقط در امتیازدهی نهایی استفاده می‌شوند و به کلیدواژه یا ranker داده نمی‌شوند.

این آزمایشِ برنامهٔ ثابت و مقالهٔ معلوم است؛ کیفیت تبدیل سؤال توسط مدل، عبور از فهرست فرمولاسیون، جواب نهایی و کیفیت بالینی را تأیید نمی‌کند. این مجموعه هنگام اصلاح وزن‌ها استفاده شده است و آزمون مستقلِ تعمیم‌پذیری نیست. `canonical_candidate_rank=null` لزوماً به معنی گم‌شدن منبع نیست؛ بعضی داروها باید از فهرست فرمولاسیون به متن کامل برسند. گزارش با مجوز 600 و بدون بازنویسی فایل موجود ساخته می‌شود؛ متن اصلی یا کلید در آن نیست.

`metrics.operations.lexical_retrieval` زمان مسیر تازه را ثبت می‌کند؛ این بازه می‌تواند داخل index_read باشد و نباید دو بار به زمان کل اضافه شود. audit هر مقاله، engine، نسخهٔ الگوریتم، تعداد نامزدها و تعداد نویسه‌های بندهای منتخب را دارد. ابزار عمومی `evaluate_reference_search` نیز حالت و نسخهٔ lexical و سقف‌ها را در مشخصات اجرای مدل ثبت می‌کند.

## مرز این فاز

چهار فراخوانی متداول برنامه‌ریزی، انتخاب بخش، پاسخ فارسی و بررسی صحت همچنان برقرارند. حذف فراخوانی انتخاب بخش مربوط به فاز سه است. کش پاسخ، connection pool مدل، deadline کوتاه کل درخواست و آزمون بار در این فاز اضافه نشده‌اند. کاهش حجم ورودی به‌تنهایی تضمین زیر ۲۰ ثانیه در تمام سؤال‌ها نیست.

## نتیجهٔ اجرای محلی

migration دوم روی دیتابیس محلی اعمال شد؛ ایندکس GIN آماده و معتبر بود و حدود ۱۴۰ مگابایت فضا گرفت. نسل کامل ۲۲٬۲۱۷ مدخلی فاز یک حفظ شد و استخراج دوبارهٔ کل منبع لازم نشد. استقرار سرور انتشار انجام نشده است.

در [گزارش آفلاین نهایی](search/evaluation/phase2-lexical-2026-11-11.json)، هر ۲۰ برنامهٔ ثابت، تمام عنوان‌های موردانتظار را در منوی حداکثر ۱۶ بخشی داشتند و ارجاع و متن تمام بندهای برگردانده‌شده با منبع تطبیق داشت. مجموع نویسهٔ عنوان و پیش‌نمایش منوها از ۱۸۴٬۸۲۷ به ۹۵٬۵۶۶ رسید: **۴۸٫۳٪ کاهش**. این عدد توکن صورتحساب نیست و فقط منوی بخش‌ها را اندازه می‌گیرد. میانهٔ میانه‌های خواندنِ سه‌بارهٔ هر مقاله حدود ۱۹۱ ms بود؛ رتبه‌بندی واژگانی کار بیشتری از خواندن سادهٔ فاز یک انجام می‌دهد و صرفهٔ موردنظر آن، کاهش ورودی مدل و دورهای پاسخ‌سازی است.

[تمام اجراهای زندهٔ مرحلهٔ اصلاح](search/evaluation/phase2-live-diagnostics-2026-11-11.json) نیز به‌صورت بدون متن پاسخ و بدون کلید ذخیره شده‌اند. این گزارش اجراهای کندِ پیش از اصلاح را هم شامل می‌شود:

| اجرا | زمان سرویس | درخواست provider |
|---|---:|---:|
| سه نمونهٔ اولیه: عارضهٔ آریپیپرازول | ۱۳٫۲۰ ثانیه | ۴ |
| سه نمونهٔ اولیه: دارودرمانی شب‌ادراری | ۱۴٫۱۳ ثانیه | ۴ |
| سه نمونهٔ اولیه: خط اول پسوریازیس | ۳۱٫۹۶ ثانیه | ۸ |
| پسوریازیس پس از اولویت مرور مدیریت | ۲۹٫۷۰ ثانیه | ۸ |
| پسوریازیس پس از وزن توصیهٔ صریح منبع | ۱۴٫۶۶ ثانیه | ۴ |

این اجراها با تنظیم خصوصی همان ارائه‌دهنده، مدل `gpt-6-luna` و reasoning برابر `none` انجام شدند؛ تنظیم فعال سرور و فایل کلید عوض نشد. مجموع این بررسی‌ها ۲۸ درخواست واقعی داشت. تغییر کد بین مرحله‌ها و تفاوت تولید مدل اجازه نمی‌دهد از این جدول یک p95 معتبر برای نسخهٔ نهایی بسازیم.

تمام اجراهای زنده از کنترل فنی متن/anchor عبور کردند؛ تطبیق سخت‌گیرانهٔ بخش مرجع در نمونهٔ اولیهٔ پسوریازیس و در نمونهٔ نهایی آن false بود. در نمونهٔ نهایی، مقالهٔ درست 5666 انتخاب شد اما مدل بند بخش «Extent and location of skin involvement» را به‌جای بخش‌های فهرست مرجع انتخاب کرد. نتیجه را به‌عنوان موفقیت کیفیِ تأییدشده نمی‌شماریم؛ بازبینی بالینی مستقل همهٔ اجراها pending است. مجموعهٔ کامل ۱۰۰ سؤال و بار واقعی اپ هنوز با مدل اجرا نشده‌اند و `release_slo_verified` همچنان false است.

۲۴۸ تست `ai_lab`، `activity`، `uptodate`، `offline` و `lexicomp` موفق شدند؛ از جمله انتخاب بخش بعد از ۶۰، یافتن بند انتهای مقاله، حفظ متن و anchor، ریشه‌یابی انگلیسی، حذف شواهد غیرمجاز، کنترل دسترسی، تشخیص کهنگی، بودجهٔ متن، برگشت با feature flag و ارزیابی آفلاین بدون فراخوانی مدل. بررسی migration نیز تغییر تولیدنشده‌ای پیدا نکرد.
